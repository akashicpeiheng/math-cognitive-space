# MCS 版本与发布协议

#MCS #研究工程 #版本管理

**一份公开结论必须同时说清内容版本、证据范围和发布状态。** 本文件是本项目的编辑与验收约定（DEF），不替代数学证明或平台规则。

## 1　修订源与版本边界

- 中文理论：原 01–16、A–E 与 cases 分章文件。
- 英文论文：`arxiv/main.tex` 与其引用、辅助材料；允许研究主线不同，但改变主张须追溯对应理论来源。
- 发布叙事：本目录导读、总纲、编排、计划与协议。
- 阅读组合：`catalog.json`；两册生成文件不手改。
- 证据：现有各验证目录的独立账本；本发布流程不写 ima 的 `progress.json`，也不覆盖认证目录的冻结进度。

两册是同一理论材料的阅读视图，不能被当成独立竞争的理论源。原章节的数学修订遵循原有核验链；只改编辑计划时不触发无关站点或笔记生产任务。

## 2　三个互不替代的状态

| 维度 | 示例 | 记录原则 |
| --- | --- | --- |
| 内容阶段 | 工作稿、编排试读稿、审阅候选、冻结版 | 说明实际完成了哪种工作 |
| 证据状态 | DEF / PROOF / REF / FINITE / ILLUSTRATION / NOT-CLAIMED | 采用第 15 章的含义；不构成可信度全序 |
| 渠道状态 | 本地、已提交、已公开、已接受 | 以真实文件、回执、网址或接受记录为依据 |

“候选稿编译通过”不改写为“已发表”；“新目录生成”不改写为“全稿重写”；“PROOF”不改写为“同行审阅通过”。本文不以匿名猜测填充任何状态。

## 3　本地试读版怎样生成和核验

版本 ID 采用 `YYYY-MM-DD-rN`，表示一次编辑快照，不表示理论正确性等级。构建脚本仅接受这种格式，把新文件写入本目录的 `releases/版本ID/`，存在同名目录时直接失败。

每个快照保存两册、其精确编排清单、27 份编排源文件快照与哈希清单。快照源文件相对路径与原理论目录一致；内部理论引用指向冻结副本。未收录的核验代码或报告链接回工作区，首页明确标注这一分发限制。构建失败可能留下待诊断目录，不自动删目录后重试；排查后用新版本名生成。

`--verify` 核对冻结输出与源快照，发现篡改或损坏以非零退出码报告。若当前工作源已有新改动，单列“源已变化”；只要冻结文件完整，旧快照仍然可以作为历史证据，不自动刷新它的哈希。纯排版、结构编排、数学内容改动在修订记录中分别说明。

原始中文整合版及旧 PDF 继续保留。首次迁移前的两个入口文档副本见 [history/20261002-before](history/20261002-before)，用于人工对比和回滚；不得用目录删除替代修订。

## 4　从本地试读版到公开版本

公开之前增加一层独立白名单封装，范围限于该版需要的内容、图表、可公开的代码、输入和报告。这里尚未实现该分发封装，不把本地快照说成脱离仓库可复现的归档物。

公开候选应具备：

1. 可独立理解的标题、摘要、读者入口、作者与版本信息。
2. 在干净目录解包可用的本地链接，源文件与所提供格式一一对应。
3. 主张、假设、证据和剩余义务的明确对应；新数学改动按原验证流程回归。
4. 精确输入、工具环境、执行命令和检查结果；PDF/网页需另做视觉检查。
5. 文本与代码分别明确的授权选择，第三方内容清单和引用信息。许可尚未选择时保持候选，不擅自宣称开源。
6. 作者对这一组具体文件的最终发布决定，以及发布后实际的平台记录。

这里只对“上传、提交、许可选择”等外部动作保留发布决定。本地编辑、检查、生成候选与修复无需每一步请求许可。本次请求的实施范围是重构与规划，未执行任何外部发布。

首次归档不使用 `latest` 或 `final-final` 作为版本号；引用包含作者、实际题名、明确版本、日期和取得的真实标识。尚无 DOI 或 arXiv ID 时直接写未取得，不造占位编号。

## 5　修订与回滚

发现问题时记录：受影响版本、原主张、发现方式、影响范围、修订源、复核结果。若改动了数学条件或证据，生成新版本并明确前后变化；旧版保留可查勘误。调整默认阅读链接只能影响入口，不能覆盖旧快照。

平台间分别记录状态：论文新版本不自动使站点同步，站点测试通过不自动使论文修订生效。由明确的来源/制品对应关系决定需要重建什么。

## 6　思想与回看

**思想：冻结的是一次可追溯陈述，研究仍然允许修订。** 方法是第 2 节的状态分列、第 3 节的源快照与哈希核对、第 5 节的影响范围记录。

回看问题：半年后有人引用某条结论，能否复原他读到的版本和那一版的证据边界？如果只能找到当前文件，“可复核”仍未完成。
