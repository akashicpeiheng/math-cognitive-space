# MCS Web：学习与研究一体工作台

从零重建的数学认知空间网站。它把专稿的理论形式落在数据模型、算法与界面上：公共数学本体 M 与公共阅读 L 分离，学习者状态 E 外置，视图与路线 D 按需读取这些数据。

主导航「MCS」提供独立的多尺度数学对象画布（`/mcs`，英文 `/en/mcs`）：远看聚合节点，放大时展开真实成员和内部声明，支持组合滤镜、拖动、本机恢复和公共视图分享。使用、当前内容边界及只读接口见 [MCS 页面](docs/MCS页面.md)。

顶栏「阅读 → Master」提供公共节点的极简数学视图：保留形式、必要条件和已有等价表达，直觉放入悬停提示；列表与网络预览同步切换。偏好保存在当前浏览器，个人笔记与学习记录不参与压缩。使用、内容维护与验证边界见 [Master 模式](docs/master-mode.md)。

2026-10-18 试点新增独立的数学对象 M 与公共阅读 L：`/objects` 提供五级形式结构、准确 Lean 目标及多篇讲解。两类 Markdown 共用 [内容协议与迁移说明](../mcs-content/README.md)；现有内容、笔记绑定与规划器继续按旧兼容协议读取。新阅读视图按需读取 M、L、E，个人更新不回写公共 M/L。

游客可直接使用学习路线；「我的笔记库」可选择本地 Obsidian 目录，在浏览器搜索、阅读与关联节点，再主动上传到私有账号。更新、历史版本、附件、备份和验证范围见[游客规划与 Obsidian 笔记库](docs/游客规划与Obsidian笔记库.md)。

「我的笔记库 → 新建笔记」现提供章节创作台：默认四项数学核心，可组合对象角色并按适用性展开历史、直觉、论证等资源；支持同篇承载、未知角色提示与完整 Markdown、预览、自动暂存、版本保存、旧稿复制和主动账号上传。节点页也可「围绕此节点写笔记」。人工指南、AI 提示词与界面共用一份模板定义；使用、迁移和恢复见[笔记创作使用说明](docs/writing/创作使用与迁移说明.md)，样稿与核验见[六类样稿审校记录](docs/writing/样稿与来源核验记录.md)，工程结果与剩余边界见[交付与验收记录](docs/writing/交付与验收记录.md)。

关系类型现统一使用 `scaling`（放缩）：两个方向保留原见证，旧 ID 继续有效。方向锥、旧记录兼容与验证范围见[放缩关系合并说明](docs/放缩关系合并-2026-10-11.md)。

## 快速开始

需要 Node.js 22.12+（开发机使用 Node 24）与 Python 3（仅证书重放需要；没有 Python 时
证书重放会如实报「无法启动检查器」，不会伪报通过）。浏览器验收另需本机
Chrome / Edge / Chromium，或在 CI 里设 `MCS_WEB_REQUIRE_BROWSER=1`（见「浏览器验收」一节）。

    cd mcs-web
    npm install
    npm run build
    npm run check
    npm test
    npm start

浏览器打开 http://127.0.0.1:3784。

**一键入口**：双击仓库根目录的 `打开MCS网站.cmd`（桌面快捷方式「MCS网站」指向它）。已在运行就只打开浏览器；没运行就先在后台启动、等到健康检查通过再打开。是否需要启动只看 `http://127.0.0.1:3784/api/v2/health`，所以重复双击不会起第二个服务进程。

    打开MCS网站.cmd                        # 仓库根目录（Windows）；打开工作台，必要时先启动
    pwsh -File scripts/open.ps1 -NoBrowser  # 只确保服务就绪，不开浏览器

后台启动与停止（默认端口 3784，可用环境变量 `MCS_WEB_PORT` 或 `-Port` 改）：

    pwsh -File scripts/start.ps1
    pwsh -File scripts/stop.ps1
    pwsh -File scripts/backup.ps1
    pwsh -File scripts/restore.ps1 -Backup runtime/backups/<文件>.sqlite3

含中文的启动脚本存为 UTF-8 with BOM，`pwsh`（7+）与 `powershell`（5.1）都能正确读取。

内置两个演示学习者（共享同一 M，确认背景不同，因而得到不同 D）：

    node scripts/seed-demo.mjs

开发模式（API 3784 + Vite 5174，前端热更新）：

    npm run dev

## 部署形态：本机 / 公网

服务有两种互斥的运行形态，由 `publicMode` 区分。默认是**本机**，刻意不提供
「什么都不配就对外开」的中间态。

| | 本机（默认） | 公网（`publicMode: true`） |
|---|---|---|
| 监听地址 | 只允许回环；写成 `0.0.0.0` 会**拒绝启动** | 由平台注入 `MCS_WEB_HOST` |
| Host 头 | 只认回环 | 只认 `allowedHosts` 白名单（支持 `*.example.com`） |
| 写请求来源 | 只认回环 Origin；本机命令行无 Origin 时放行 | **必须**带 Origin 且等于 `publicOrigin` |
| 身份边界 | 无（单人使用，档案是本机文件） | 账号体系；未接入时**拒绝启动** |
| 安全响应头 | CSP 等统一挂载 | 同左 |

公网模式的自检在 `server/deployment.mjs`，由 `startServer` 在**监听端口之前**调用；
账号配置本身由 `server/auth.mjs` 的 `validateAuthConfig` 逐项校验。两者都在监听之前，
所以任何一项不合格的结果都是**进程起不来**，而不是"起来了但谁都能写"。

### 身份与权限（`server/auth.mjs`、`server/api.mjs` 的权限表）

| 能力 | 访客 | 已登录用户 | 管理员 |
|---|---|---|---|
| 读公共本体 / 证据 / 研究索引 | ✓ | ✓ | ✓ |
| 纯计算（关系合成、局部化算子、形式校验） | ✓ | ✓ | ✓ |
| 路径规划、学习方案预览、路线阅读与结构回放 | ✓（游客草稿、有配额） | ✓（有配额） | ✓ |
| 浏览器本地 Obsidian 笔记库 | ✓（当前浏览器） | ✓ | ✓ |
| 账号私有笔记库上传、读取与独立导出 | ✗ | ✓（仅自己的，跨档案共用） | ✓（仅自己的） |
| 证书重放、辅导会话 | ✗ | ✓（有配额） | ✓ |
| 个人档案、事件、笔记、网络视图、导入导出 | ✗ | ✓（仅自己的） | ✓ |
| 入库 / 发布 / 撤回 / 全站备份与恢复 / 维护视图 | ✗ | ✗ | ✓ |

- **登录方式**：GitHub OAuth（带 state + PKCE）与邮箱密码（注册 / 验证 / 找回 / 改密 / 退出）。
- **会话**：服务端会话表 + `__Host-` 前缀 Cookie（HttpOnly、Secure、SameSite=Lax），
  载荷用 AES-256-GCM 封装；公网模式下所有写请求都要带 `x-mcs-csrf` 令牌**且**来源与站点一致。
- **必须跑在 https 上**：`__Host-` 前缀要求 `Secure`，而浏览器**拒收** http 页面下发的
  `Secure` Cookie。也就是说公网模式在 http 下不是"不安全"，而是**登录根本走不通**
  （写请求会被 CSRF 拦掉）。本机模式（http://127.0.0.1）不受影响：那里没有账号，
  走的是来源校验那条分支。
- **归属**：私有对象按服务端认证身份判定归属；不是自己的对象与"不存在"同形（404），
  不用 403 区分——那会变成档案 id 的存在性探针。
- **权限表默认最严**：`server/api.mjs` 里未登记的路由按管理员处理，新增接口忘了登记时
  错在关门，不在开门。
- **任务配额**：全站并发 1、队列 20、每账号或匿名 Cookie 1 运行 + 1 排队、单任务 60 秒，超出当场报 429。游客不可用 `sync` 绕过队列，匿名归属标识仅存于服务端。
- **管理员**按认证服务的用户 id 显式配置（`auth.adminUserIds`），不采用"首位注册者即管理员"。

### 存储：本机 SQLite / 公网 PostgreSQL（2026-10-05）

学习数据（档案、事件、笔记、网络视图）与账号数据（会话、OAuth 中间态、对象归属）
走同一个**统一异步存储接口**（`server/sql-driver.mjs` + `server/db.mjs`），驱动二选一：

| | 本机（默认） | 公网 |
|---|---|---|
| 驱动 | SQLite（`node:sqlite`，`db.file`） | PostgreSQL（`dbUrl`） |
| 备份 | **物理备份**：复制数据库文件 | **逻辑备份**：整库导出 JSON，恢复时整库回填 |
| 事务 | 连接级 `BEGIN IMMEDIATE` | 连接池 + `AsyncLocalStorage` 绑定事务连接 |

- 语义只有一份实现（事件去重、revision 冲突、分页游标、导入全有或全无）——
  两份实现漂移会让「同一份导出，本机与公网结果不同」，那是数据事故，不是风格问题。
- **公网模式强制要求 PostgreSQL**：容器本地 SQLite 在重启 / 换实例时整个消失，
  所以缺 `dbUrl` 时**拒绝启动**，而不是"先跑起来再说"。
- 事务连接绑在**异步调用链**上，不绑在驱动实例上：后者会让并发请求卷进同一个事务，
  互相看见对方未提交的数据（低并发下几乎测不出来）。
- 环境变量：`MCS_WEB_DB_URL`（或平台常注入的 `DATABASE_URL`）、`MCS_WEB_DB_SSL`、`MCS_WEB_DB_POOL_MAX`。

必填配置项：`publicMode`、`publicOrigin`（https 根地址）、`allowedHosts`（服务域名白名单）、
`dbUrl`（PostgreSQL 连接串）、`auth.mode = "supabase"`、`auth.url`、`auth.publishableKey`、
`auth.sessionKey`（32 字节随机数的标准 base64）、`auth.adminUserIds`。
对应环境变量：`MCS_WEB_PUBLIC_MODE`、`MCS_WEB_PUBLIC_ORIGIN`、`MCS_WEB_ALLOWED_HOSTS`、
`MCS_WEB_DB_URL`、`MCS_WEB_AUTH_MODE`、`MCS_WEB_AUTH_URL`、`MCS_WEB_AUTH_PUBLISHABLE_KEY`、
`MCS_WEB_AUTH_SESSION_KEY`、`MCS_WEB_AUTH_ADMIN_IDS`、`MCS_WEB_AUTH_EMAIL_ENABLED`、`MCS_WEB_AUTH_FILE`。
凭据只从环境变量或 `config.local.json`（已被版本控制排除）读取，不进代码、不进前端构建产物。

## 中英双语（2026-10）

站点有中英两版，顶栏有一个「中文 / EN」切换按键。这一节的约定属于**结构**，改代码前请先读。

- **交付状态与剩余缺口**：[`docs/中英双语交付说明.md`](docs/中英双语交付说明.md)
  （含可复现的验证命令与当时的输出、这一轮工具链抓到的真缺陷、两处「如实天花板」）
- **施工基准**：[`docs/i18n-施工手册.md`](docs/i18n-施工手册.md)
  （硬规则、术语表用法、踩过的坑、**工具查不到必须人看的清单**）

### 三条不变量

1. **中英是同一份本体、同一个版本**。语言覆盖在 `createOntology()` 算出 `contentHash` **之后**
   才应用（`data/i18n/overlay.mjs`），所以 `zh` 与 `en` 的 `ontologyVersion` 逐字相同。
   这不是省事：档案与事件挂在 `ontologyVersion` 上，两个哈希等于两套互不可见的证据
   ——「换个语言就看不到自己的学习记录」。
2. **只换文本，不换结构**。节点/行动/证据/关系的 id、`discipline`、`construct`、`roles`、
   `mode`、证据标签（`DEF` / `PROOF` / `REF` / `FINITE` / `ILLUSTRATION` / `NOT-CLAIMED`）、
   LaTeX 与公式一律不动。结构差异由 `scripts/i18n-parity.mjs` 当场判错。
3. **缺译文 = 回落中文 + 如实标注**。不会变成空白，也不会编一段英文。英文站的未译条目带
   `i18n-pending` 标记与提示，缺口逐条列在覆盖率报表里。

### 语种从哪来

| 层 | 机制 |
|---|---|
| URL | 中文在根路径，英文在 `/en/…`（同一棵路由树挂两次，见 `web/src/App.tsx`）；`/zh/…` 重定向到无前缀版本 |
| 前端 | `web/src/i18n/`：`I18nProvider` 从路径前缀读音种，写 `<html lang>` 与 `<title>`；`api.ts` 的 `setApiLocale()` 让**所有**请求自动带 `?locale=en` |
| 后端 | `server/api.mjs` 的 `resolveLocale()`：`?locale=` ＞ `x-mcs-locale` 头 ＞ 默认 `zh`。未知语种回落 `zh` 并在响应头 `x-mcs-locale` 里如实回报 |
| **不读** `Accept-Language` | 浏览器每次都自动带它，用它协商会让「分享出去的英文链接在中文浏览器里打开变成中文」——路径前缀已经表达了意图 |

### 文案放哪儿

| 类型 | 位置 |
|---|---|
| 通用壳层（导航、按钮、通用动作、无障碍标签） | `web/src/i18n/messages.ts`，**中英成对**写（漏一个键就编译不过） |
| 受控词表的显示名（构造类型、角色、关系种类、学科…） | `web/src/labels.ts` 的成对表；组件用 `useLabels()`（在 `web/src/i18n/useLabels.tsx`） |
| 页面自己的长文案 | 该页文件内的成对表，不要往 `messages.ts` 堆 |
| **本体里的文本**（节点标题、摘要、动机、证据说明、正文） | `data/i18n/en/`，由服务端按语种下发 |

`web/src/labels.ts` **不许 import React**：它被纯 Node 测试直接 import
（`tests/relation-visual.test.mjs` 等），一旦依赖组件目录，那几套测试会以
`ERR_UNSUPPORTED_DIR_IMPORT` 整体失败——这条踩过，写在 `web/src/i18n/useLabels.tsx` 的文件头。

### 内容翻译怎么加

```bash
node scripts/i18n-inventory.mjs                    # 本体里哪些字段含中文、各多少字
node scripts/i18n-extract.mjs --case manifold --out tmp/i18n/manifold.zh.json
npm run check:i18n                                 # 两道门：结构对等 + 正文公式逐字
npm run i18n:todo                                  # 还差哪些条目
```

覆盖文件按案例放在 `data/i18n/en/`，**必须在 `data/i18n/index.mjs` 的 `REGISTRY` 里登记**
才会被装配（登记是按文件逐条容错的：某个文件还没建 = 那一块记为缺口，其余照常生效；
**没登记 = 白写**）。译者须知见 [`docs/i18n-施工手册.md`](docs/i18n-施工手册.md)。

### 两道门的分工（都不要绕过）

| 工具 | 查什么 |
|---|---|
| `scripts/i18n-parity.mjs` | 全部字段：id 是否存在、数组长度是否按序对齐、受控值是否被改写、数字/量词/证据标签计数是否一致、散文里是否残留中文 |
| `scripts/i18n-block-check.mjs` | 只查正文块，但更严：公式**逐字**相同（行内公式允许换序，内容与个数仍严格）、标题层级一致、`/nodes` 链接正文逐字/文献节不许多出 |

**两道门都不检查数学正确性**——把「不收敛」译成「收敛」它们看不出来。译文与中文源的
对应关系仍需人工抽样复核，这一点写在每个覆盖文件的文件头，不许把「parity 通过」读成
「译文已核对」。

人工复核清单（工具查不出、只能人看）：
- `dg:method-closed-form-test` 的中文标题「在原点上验证闭形式是否恰当」疑似「区域上」的笔误
  ——**照源译出，未替源改错**；
- 微分流形（`Differentiable manifold`）与光滑流形（`smooth manifold`）在英文里**故意不统一**：

- 公式里 `\text{…}` 内部的说明文字是唯一允许改动的公式内容（中文字符不能出现在英文站上）。

## M / E / D 边界
- **M（公共本体）**：data/ 中的版本化文件。装配时计算 SHA-256 作为本体版本；节点、证据、行动与硬关系不因学习而变化。学习过程中没有任何写入 M 的接口。
- **E（外部模型）**：本机 SQLite（默认 runtime/mcs-web.sqlite3）。保存档案、事件、确认、作答、误区实例、能力估计与个人笔记；事件 ID 去重，修订号检测多标签页冲突。
- **D（派生结果）**：局部化视图、候选路线、位置化复习与检查结果。结果包保留事件、来源、偏序、见证与版本；不写回 M。

Adapt 与 Loc 分开：Adapt(E,s,g,b) 只产生显式参数包 θ；Loc_λ(M) 只读公共结构。需要直接读取 M 的入口在代码中单独命名为 adaptWithOntology（对应专稿的 Adapt_M）。

## 学习闭环

学习者的每一次状态变化都是 E 里的事件，界面只是它的投影：

| 动作 | 写入 E 的事件 | 语义 |
|---|---|---|
| 标记已读 | `view` + `payload.context='read'` | 读过，**不表示理解或掌握** |
| 我还不懂 | `view` + `confirmation{confirmed:false}` | 读过但没懂；进入待复习队列 |
| 确认已掌握 | `confirmation{confirmed:true}` + `view` | 唯一能把节点放进 θ.known 的路径 |
| 自检作答 | `answer` | 外部模型的观察，不自动判对 |
| 记一次复习 | `view` + `payload.context='review'` | 复习次数 +1；不改变掌握状态 |

θ 因此分成彼此独立的两条轴：**可用性**（`known` / `unknown` / `unspecified`）与**阅读**（`viewed`，含 `reviewCount`）。已读节点仍然算「未指定」，因为读过不是可用性声明。

前端派生层在 `web/src/learning.ts`：计数、「现在可以新学」（引入行动的全部输入已确认）、「还差什么」（缺哪些输入）、待复习队列。它给出的定义与 LC20「认知前沿」一致；在无 θ 时作为本地回退。

**2026-10-11 口径归位**：`ready` / `blocked` 现在**排除话题级条目**（`granularity === 'topic'`），
与 `starting-nodes.ts` 的起始节点同口径；被排除的条数在 `threadExcluded` 里如实报出。
在此之前两处口径不同——同一个话题会在一处是「现在可以新学」，在另一处连起始节点都不是。

**明确不做**：不给掌握度百分比，不做间隔重复与到期日排序。M 与 E 里都没有校准过的认知模型，伪造数字会误导学习者；复习只有「位置化插入」与「次数计数」，不承诺记忆效果。

## 起始节点与默认档案模板（2026-10）

两件事合起来回答同一个问题：**「按我现在的档案，我能从哪儿开始？」**

### 起始节点是什么

一份档案下的**单元级**节点 n 是起始节点，当且仅当三条同时成立：

1. **尚未确认**——n 不在 θ.known 里（确认过的节点不需要「开始」）；
2. **登记的前置都已确认**——
   - 每条指向它的 `hardPrereq` 关系的**来源**都在 θ.known 里（硬前置是「不用它就定义不出来 / 推不下去」，
     因此逐条满足，不能任选）；
   - 并且要么**没有任何行动能产出 n**（背景接口只能由学习者自己声明），
     要么**存在一个**能产出 n 的行动，其**全部输入**都在 θ.known 里（同一节点常有多条引入路径，任一条走得通就够）；
3. **不是话题级条目**——`granularity === 'topic'` 的是学习线索的名字，本来就不参与前置计算。

判据只有这一处实现：`web/src/starting-nodes.ts`（纯函数，node 可直接 import）。它是 **D 层的派生**——
输入是本体的投影（节点 / 行动 / 关系）与这份档案的 θ，因此**换档案、确认一个节点，标记就跟着变**：
起始节点不是视图的属性，是档案的属性。

与 `web/src/learning.ts` 的 `ready`（「现在可以新学」）的关系：`ready` 是**只看行动契约**的宽松口径，
用在「我的学习」概览；起始节点是**契约 + 硬前置**的严格口径，用在知识网络。
两者的差集不是噪声，而是「契约齐了、硬前置还差」的节点，`deriveStartingNodes` 的 `blocked` 里逐条给出缺谁。

### 界面上落在哪里

| 位置 | 表现 |
|---|---|
| 网络视图的卡片 | 卡片外一圈**绿色描边** + 右下角「起始」徽标 + `<title>` 里一整句依据（由哪个行动引入、哪些输入已确认，或「没有任何行动能产出它」） |
| 网络视图的图例条 | 「起始节点 N / 总数」一项，仅在该视图真有起始节点时出现；提示里写全判据，并写明**它不是难度标签** |
| 「推荐加入」面板 | **空网络时推荐的就是起始节点**（从前只推荐背景节点——对已经声明过前置的学习者是错的）；条目上另加一枚「起始」徽标，与推荐理由徽标并排（理由回答「为什么放到你眼前」，起始节点回答「按你的档案能不能开始」，两件事都要说） |
| 节点详情面板 | 选中起始节点时写出同一句依据 |
| 「我的学习」概览 | 一张「起始节点」卡片：前 8 个 + 总数 + 去网络视图的入口 |

**刻意不做**的一件：**没有**把起始节点提到推荐列表各组最前。试过，撤回——那会改掉
「空网络 → 跟着推荐点三下就能连成一张图」这条链（实测点出来的三个节点之间 0 条边，
`tests/browser.mjs` 的「加入多个节点后出现边」当场红）。推荐顺序本身有含义
（理由强弱 → 关联数 → id，见 `network.ts` 的 `recommend`），起始节点是另一个维度的事实，不该改写它。

### 默认档案模板：空白 / 高一 / 大一新生

`data/profile-templates.mjs` 是**公开、版本化的初始声明**：某个学习阶段通常已经学完哪些数学内容。
建档案时选一个，服务端就把 `declares` 里的节点写成一串 confirmation 事件落进 E。

| 模板 | 阶段 | 声明 | 效果（实测，起步为空白档案） |
|---|---|---|---|
| `blank` 空白档案（自己声明） | 不预设任何已学内容 | 0 条 | 起始节点只剩不需要任何登记前置的那些（8 个背景接口 + 本体里没有登记输入的节点） |
| `high-school-1` 高一 | 完成义务教育阶段数学 | 2 条：等式与替换、实数度量背景 | 起始集合扩大到 13 个（新解锁：实数距离、四个证书片段等） |
| `university-freshman` 大一新生 | 完成高中阶段数学 | 4 条：再加量词、函数与复合与逆 | 起始集合扩大到 15 个（再解锁置换群、等边三角形的刚性对称、有续域、`liang` 的拓扑空间等） |

三条纪律，写在文件头也写在代码里：

1. **不进 M**：模板不参与 `data/manifest.mjs` 的装配，因此**不改 `contentHash`**。
   它是 E 的初值，不是本体的一部分——改模板不会让已存档案的 `ontologyVersion` 失配。
2. **只声明背景接口节点**（`case === 'background'`）。那九个节点是本站对环境边界的显式声明，
   语义上正好是「学习者应当已经具备的前提」；案例节点（`limit:` / `dg:` / `top:` …）是本站要**教**的内容，
   模板一旦声明它们，「起始节点」就变成伪造的进度。这条由 `validateProfileTemplates()` 强制，
   `npm run check` 的 `[9]` 节与 `tests/starting-nodes.test.mjs` 都会核对。
3. **声明 ≠ 测评**：事件带 `source.kind = 'system'`、`ref = 'profile-template:<id>'`、
   `payload.declared = true` 与 `payload.basis`（依据原文），事后能分清「他自己确认的」与「模板代写的」；
   界面在模板预览里逐条列出依据，并写明不认同的一条可以标为尚未确认。

接口：`GET /api/v2/profile-templates`（公共只读，模板文案中英成对下发，节点标题随请求语种）、
`POST /api/v2/profiles` 接受 `template` 字段（未知模板**当场拒绝**，不静默回落成空白；
逐条写入、部分失败进 `failed` 并带原因，不假装全有或全无）。

### 默认档案：`高一` 与 `大一新生` 是**真的两份档案**

模板只是「建档案时可以选什么」。用户要的是打开站点就能在「学习者档案（E）」下拉里**看见**这两份，
所以还有一层落地：

    node scripts/seed-default-profiles.mjs     # 幂等：同名档案已存在就跳过，不覆盖、不追加

- 建出来的是 `kind: personal` 的普通档案（不是 `demo`：它们给真实学习者用），事件与接口建的一模一样
  ——两处共用 `server/profile-templates.mjs` 的 `applyProfileTemplate()`，不许各写一份事件形状；
- **同名即跳过**：用户自己建过、改过、甚至删过模板事件，脚本都不会盖回去；想重建先删同名档案；
- 界面上的三个入口，都通向同一个接口：下拉里的「＋ 新建档案（选模板）…」、
  「我的学习」还没有档案时的两张模板卡、以及「高级设置」里的模板下拉（那里逐条列出依据）。
  这一条是 2026-10-11 用户反馈「没看见学习者档案」之后补的：模板原先只存在于「高级设置」的一个下拉里。
- 档案名是**学习者自己的数据**（E 层），英文站上不翻译：`data-i18n-keep` 标着，
  `scripts/i18n-ui-scan.mjs` 因此不会把中文档案名报成「漏译的界面文案」。

### 如实登记的边界

- **判据就是已登记的数据，不额外补常识**。因此某条行动契约漏登记了输入时，这个节点会**过早**成为起始节点。
  实测到一条：`a-dg:inverse`（引入反函数定理）的输入只登记了 `bg:real:metric` 与 `bg:linear:vector`，
  没有 `bg:manifold:calc`——于是选了「大一新生」模板时，**反函数定理**会成为起始节点。
  这是**登记口径的已知边界**，不是本功能的结论；本轮**不改 M**（改契约输入会换 `contentHash`，
  让已存档案的版本失配），只把它写在这里与 `starting-nodes.ts` 的文件头里。
- **起始节点不是难度标签**，也不代表本站测过任何人的能力：它只说「已登记的前置，在你的档案里都确认过了」。
- 起始节点**不含话题级条目**；它由 8 个背景接口与少数没有登记输入的节点兜底，这两类在空白档案下也会出现。
- **2026-10-11 修好一处判据混用**：从前「契约里的一条输入算不算数」被误用成「它是不是单元级」，
  于是以**话题级条目**为输入的契约被判成「输入为空」——实测 10 个节点（`rudin:set-function`、`top:claim-a2-a1` 等）
  会在空白档案下冒充起点。现在两个集合分开（`resolvable` 管「算不算数」、`unitIds` 管「是不是单元」），
  空白档案下的起始节点仍是 8 个（它们恰好都不是那一类），但 `blocked` 的名单因此更准。
  这条口径现在由 `isStartableUnit` 一处承担，方向层（`web/src/direction.ts`）调用的就是它。

## 学习引导与路径安排（2026-10-12，当前实现）

「开始学习」采用次级学科兴趣与已有目标两种入口，选择后立即展示主目标、近期里程碑、
第一步、背景核对、3–5 步预览及全局依赖图。学法与节奏为可选设置，支线由学习者主动加入。

学习安排复用现有 AND/OR 规划器，按实际候选补齐硬前置，并对规范化事件图做拓扑排序。

## 学习方向与并行节点的排序（2026-10-11，历史设计）

本节记录此前方向面板的设计与当时检查。页面流程和档案级排序以 2026-10-12 实现说明为准；
旧方向纯函数与缓存为兼容保留，当前可学集合只依据已确认知识。


**要解决的那句话**：让学习者经过初步探索之后能马上知道自己要学什么；把逻辑上可以并行的
待学习节点，按自己的需求和兴趣合适地分配到线性的学习路径里。

### 为什么需要这一层（实测）

| 事实 | 数字（**2026-10 设计时的实测快照，非现值**；现值读 `GET /api/v2/health`） | 怎么来的 |
|---|---|---|
| 站点登记 | 231 节点 / 252 行动 / 184 关系 / 118 硬前置 | `GET /api/v2/ontology/graph`（本体 `sha256:6b569d15…`） |
| **空白档案下「现在就能开始」** | **8 个**（全是没有任何行动能产出它们的背景接口） | `deriveDirection().options`，见 `tests/direction.test.mjs` |
| 「高一」档案（已确认 2 条背景）下 | **11 个** | 同上 |
| 一站式的排序依据 | **此前没有**：`ready` / 起始节点只说「能不能开始」，不说「先学哪个」 | `learning.ts` 头部的三条纪律 |

一句话：**22 个平权的绿色徽标等于没有方向**。这不是内容缺失，是排序依据缺失。

### 三个概念（判据只有一处实现）

| 概念 | 定义 | 在哪 |
|---|---|---|
| **可用（startable）** | 单元级节点 n：未确认；每条指向它的 `hardPrereq` 来源都已确认（AND）；且要么没有任何行动能产出它，要么存在一条产出行动其**全部可解析输入**都已确认（OR） | `web/src/starting-nodes.ts` 的 `isStartableUnit` —— **唯一实现**，起始节点徽标与方向选项表都调它 |
| **前进层** | 把 θ 加上 n 之后**新变成可用**的节点（只做一步） | `direction.ts` 的 `unlockOf` |
| **方向核心（core）** | 声明方向 g 的必需集合：从 g 出发沿「指向它的硬前置」与「产出它的那条行动的最佳输入」反向收到不动点 | `direction.ts` 的 `coreNodes` |

**为什么不做传递闭包**：实测（当时 231 节点 / 118 硬前置）每个可用节点算出来的传递闭包都是 **108**——
这个数字没有区分度。一步计数才有信息量，因此判据 4 说的是「现在能用它接着开始几个」。

### 排序判据（五条，字典序，不用加权分数）

1. **方向内优先**：`n ∈ core` 排在前面（这就是「按自己的需求和兴趣」的落点）；
2. **只能由你声明的优先**：没有产出行动的背景接口排在同类之前；
3. **学法偏好**（第四问，可选）：同在上一档时先给偏好的一类（`MOOD_CONSTRUCTS`）；
4. **新解锁多者优先**：确认它之后本体的可用集合扩大几个；
5. **登记顺序**：前四项完全并列时按本体 `nodes` 数组序，保证两次调用逐字相同。

**条款 4 的措辞纪律**：它说的是「现在能用上它做出什么」，**不是「更重要」**，也不是难度。
界面上那句话由 `optionBasis()` 生成，页面不许各写一句。

### 被迫 / 可选（让学习者知道自己在哪里真的能选）

记 `m = |core ∩ 可用|`：`m ≤ 1` 判为**被迫**（现在只有这一条通向方向，其余选项如实标成「不在这个方向上」）；
`m ≥ 2` 判为**可选**（先走哪条不影响「能不能到」，只影响路上顺手拿到什么）。
门槛是 `PARALLEL_THRESHOLD = 2`（登记在 `data/design-values.mjs`）。

### 界面落在哪四处

| 位置 | 做什么 |
|---|---|
| `/start` 的「接着上次」卡片顶部 | 方向块：没方向就挑（案例终点预设 + 按名称搜索）；有方向就给「位置 → 下一步 → 完整选项表 → 预览 → 路径 → 核心」 |
| `/profile` 概览 | 与「起始节点」卡片并列的方向卡（同一份派生，`compact` 只省掉重复的长列表） |

### 三层边界（写进代码，也写在界面上）

| 东西 | 存在哪 | 为什么 |
|---|---|---|
| **方向声明**（「我要去哪」） | **E 层**：`learning_directions` 表 + 一条 `kind: 'goal'` 事件（`payload.intent = 'direction'`） | 它是学习状态：跟着档案走、随导出带走、跨浏览器。表是快查镜像，事件是导出与审计的事实来源 |
| **决策账本**（「我选了先学这个」） | 本机 `localStorage`，键按档案分开（`mcs-direction-decisions-v1:<profileId>`） | 它是**会话上的打算**，不是学习事实；写成事件会污染事件流 |
| **已确认** | E 层既有 θ | 唯一能把节点判成「可用前置」的东西 |

**因此「选择了」从不冒充「会了」**：`position.confirmedUnits` 与 `position.adoptedSteps` 分开显示，
`adopt()` 不写 θ。路径是每次从 `θ + 方向 + 账本` 重算出来的（`direction.ts` 逐步复算），
因此别处确认了某个节点，路径自己会把它标成 `confirmed`；本体换了版本、节点不可解析，标成 `stale` 并如实说出来。

### 如实登记的边界

- **方向核心可能成环**。实测 `tensor:end-iso` 的核心在「行动输入 + 硬前置」口径下有环
  （`t-univ` 的输出同对又成了它自己的输入）：这时 `core.unresolved` 列出拆不开的那几个，
  `core.levels` 里**不出现**它们，`truncated` 如实为 true —— 不伪造层号，也不假装一条通顺的路。
  界面据此说明「这不是『先学哪一个都行』，而是『按当前登记，这个目标不能靠一条通顺的次序走到』」，
  并给去 `/plan` 做可行性判定的入口。
- **判据就是已登记的数据，不补常识**：`a-dg:inverse` 那条漏登记的输入仍然会让反函数定理过早可开始
  （与「起始节点」一节记的是同一条边界，两处共用一份判据，因此不会一处修好一处没修）。
- **不给难度、不给时长、不给百分比**；排序需要的东西只有上面五条。
- **方向不是兴趣画像**：浏览记录**不参与**排序。程序不替学习者猜兴趣；方向只来自显式声明。

`scripts/build-dg-case.mjs` 是生成器，做三件事：从只读快照 `data/dg/*.md`（30 个源文件的副本）提取元数据、归一化标题层级、**重写 `[[wiki 链接]]`**。

#### 与已有登记重合的概念怎么处理（**不重复登记**）

站点里已经有同一对象的其它登记（例：`liang:lie-derivative`、`top:separation-axioms`、`rudin:contraction-principle`）。规则是 `data/merges.mjs` 文件头的三条不变量，判定依据是**构造类型 + 粒度是否相同**，不是标题像不像：

- **同对象、同粒度** → 在 `MERGE_GROUPS` 里收成一个规范节点（`canonical` 选已有 id，`differences` 逐条写清两处登记的差别）。装配期会把被合并的登记逐字挂到 `registrations` 上，**连正文块一起**（`core/ontology.mjs` 的 `withContent`），因此新世代正文照旧显示，站点上也不会出现两个同样的点。
- **构造不同 / 粒度不同** → 不合并，写进 `KEPT_SEPARATE` 并写明理由。例：`rudin:contraction-principle` 是 `Claim`（Rudin 书里的定理 + 证明证据），概念版的「压缩映射原理」不是同一个对象。

## 教材凝练路径（第六个案例）

梁灿彬、周彬《微分几何入门与广义相对论》上册（第二版），科学出版社，2006
（现代物理基础丛书 7，ISBN 978-7-03-016460-5，xi + 442 页，共 10 章）的**凝练路径**：
把整本书压成 57 个里程碑节点，按教材的自然接缝分成七程，每一程都能在规划器里当场跑出路线。

### 来源怎么核验

本机只读扫描件在 `reference/`（464 页）。**该扫描件的文本层是有损的**：抽样只有 111 个不同字形码，
汉字无法还原（这一点是实测出来的，不是推测）。因此本站**不引用扫描件的文字**，只引用它的**目录结构**——
章节号（§1.1 … §10.5）与印刷页码在文本层中未受损，逐行抄录后与科学出版社官网图书页公布的目录对齐，
两处一致（章节划分、小节编号、页码区间全部吻合）。

知识点清单依据项目内既有目录
`ima-geometry-notes/nodes/catalogs/梁灿彬微分几何与广义相对论知识点节点.md`
（该联接指向 `E:\automation\_producing\_nodes`）。原清单是按「分类 + 对象列表」组织的全书条目，
本案例把它**凝练**为上册十章各 3–7 个里程碑，**不是逐条搬运**，也不含下册专题。

### 本体侧的登记

| 项 | 数量 | 说明 |
|---|---|---|
| 概念节点 | 41 | 用 `concept()`，`predicate` 写成该对象在该节的分类谓词 |
| 断言节点 | 16 | 积分定理、Birkhoff、测地偏离、场方程、施瓦西解等；角色分 `Theorem` / `Property` / `Axiom`（场方程是公设，显式标注） |
| 方法节点 | 3 | 指标配平（局部）、度规到曲率的固定流程（局部）、用 Killing 场换守恒量（全局） |
| 误区模式 | 3 | 曲率必须靠嵌入、克氏符当张量、宇宙学红移当多普勒；都带教材使用的对照例子 |
| 行动契约 | 63 | 输入是该节点在教材里**真正**依赖的前置节点，不是「同一章里排在前面」的节点 |
| 关系 | 10 | `scaling` / `application` / `crossDomain`（与本站 dg、tensor 案例以及 `bg:top:space` 对接，不新建重复节点） |
| 证据 | 63 | **一律 `reference` / `checkStatus: not_run`**，`reference` 写到章节号，`obligations` 写明「未编码为 ND 证书」与「未逐页核对教材原文」 |

**证据纪律**：本站正文是**凝练笔记**，不是教材原文的替代，也没有转录教材中的完整证明。
因此证据一律登记为 `reference`（引用教材），`status` 按「教材里有什么」取值而不是按「本站证明了什么」：
概念类取 `DEF`，教材给出论证的定理取 `PROOF`（含义是「教材有论证」，本站既未转录也未复核），
爱因斯坦场方程这类公设降为 `DEF`。
`teaching.evidenceStatus` 同样只表示「该命题在教材中有论证」，不表示本站验证过那份论证。

### 规划页：目标可以留空（2026-10-13）

「确定目标」是三步主线的第一步，但它现在是**可选**的。要点是：**规划器契约里目标仍然必填**
（`shared/contracts.mjs` 的 `normalizePlanRequest` 里那条 `至少需要一个目标节点` 没动——
没有目标就没有「要走到哪」，硬塞一个空目标只会得到 400）。「可选」指的是**表单上可以留空**，
那时页面换一条**已有的**派生来回答另一个问题：

| 目标 | 页面给出的东西 |
|---|---|
| 选了 | 照旧：`POST /api/v2/plans`，比较路线（③ 比较路线） |
| **留空** | **不发规划请求**：当场算**可学前沿**——按声明的背景，本体里现在就能开始的节点 |

- 可学前沿用的是「我的学习 / 开始页」那张下一步表的**同一份派生**
  （`web/src/direction.ts` 的 `deriveDirection`，θ = 本次表单里背景声明的键集），
  因此同一页面上不会出现两套「什么算已会」；每条候选的**依据句**也直接来自
  `optionBasis`，界面不自己写第二句。
- 结果卡（`.plan-frontier`）如实给出四个数：现在就能开始 / 背景够得着（x / y 个单元级节点）/
  这份背景声明几项 / 有多少**话题级条目被排除**在可学集合外（它们是线索的名字，不是可学的单元）。
- 候选分两类，**动作不同**：
  - **有产出行动**的节点 → 「用它当目标」：写进下拉框并立刻规划一次；
  - **没有产出行动**的节点（本体的 `Symbol` 这类，`deriveDirection` 的 `actionId === null`）→
    「标记为已有」：它**当不了目标**（规划器只能靠事件产出节点，选它必然「界内不可行」），
    标记后立刻计入背景声明，前沿当场重算——界面把这条理由写在按钮的 `title` 上，不假装它能当目标。
- 顺带修掉一个既有小毛病：`?goal=` 指向的节点若不在下拉框的常规构造类型里（符号类），
  `value` 落不到任何 `<option>` 上，浏览器会把下拉框显示成**空**（看起来像没选目标）。
  现在会为「当前目标」补一条选项。

### 路径规划页的「范例路径」栏目

规划器只有「目标 + 背景 + 事件界」三个输入，第一次来的人既不知道该填哪个目标，也不知道背景该声明什么。
`/plan` 因此有一个 **范例路径** 栏目（`web/src/example-paths.ts` + `web/src/components/ExamplePaths.tsx`），
目前有**四套教材样本**（梁灿彬、Rudin、简明高等代数各七程，Axler 九程），各给出一程的**特色简介**、覆盖章节与页码、目标、起点、
实测事件数与事件界，点「载入并规划这一程」会把目标组、事件界与起点声明写进表单并立刻规划。

#### 压缩态 → 悬浮简介 → 点击展开（2026-10-13 第二版）

用户的要求：「这一栏太臃肿了，改成最初是压缩状态，让用户按学科选书，鼠标悬浮在书名的时候
显示这个路径的介绍，点击后展开具体路径。」因此这一栏现在只有**三层**，默认只占几行：

| 层 | 什么时候出现 | 内容 |
|---|---|---|
| 学科分组 | 一直显示 | 「分析」「线性代数」「相对论与宇宙论」各一行，右侧是该学科的书名按钮 |
| 选书按钮 | 压缩态 | 书名（`shortTitle`）+「7 程 · 47 个里程碑 · 每程 4–10 个事件」+「展开这 7 程」；**一程卡片都不渲染**（Axler 那本是 9 程） |
| **整条路径** | 压缩态（每本书一个） | 「整条路径」按钮：**一键导入整条路径**，不用先展开——载入第一程并挂出各程进度轨 |
| 路径简介与**取舍** | **悬浮书名或键盘聚焦** | 教材全名、这套路径讲什么（`lead`，限两行）、学科分布；**特色 / 优点 / 代价与局限各 3 条** |

#### 一键导入整条路径（2026-10-13 第四版）

一程一程点「载入并规划这一程」要七次（Axler 那本九次），还得自己记住走到哪；因此每本书多了一个
**整条路径**入口。点下去之后：

1. 立刻把**第一程**的目标、事件界与起点写进表单并规划一次（和单程载入同一条路径）；
2. 表单下面挂一条**各程进度轨**（`.example-walk`）：每一程一行，写着这一程的里程碑数、
   起点项数与实测事件数，状态分「当前 / 本次已载入 / 未开始」；
3. 点任意一程可直接跳过去，也可以按「下一程：第二程 ……」正序走。

几条约定，都写进了代码注释与 VALIDATION：

- **它记的是「本次会话载入过哪几程」，不是学习进度**：载入范例写的是示范假设
  （`kind: 'assumption'`），不改公共本体、不产生 E 层事件。因此状态存在 `sessionStorage`
  （`mcs-example-walk-v1`），关掉标签页就消失；留在 `localStorage` 会让人误以为那是学习记录。
  界面上也一律用「载入」而不是「学会」，并用「结束整条路径」清掉会话状态。
- **起点仍然由前几程累进**：`path.entries` 本来就是「基础背景 + 前面各程的里程碑」，
  整条路径只是把它按顺序交出去，不额外发明依赖。
- **窄屏**：这一栏仍排在规划表单之后（`PlanPage` 的 `useMediaQuery('(max-width: 860px)')`），
  进度轨紧跟表单，手机上一样能用（进度轨在窄屏收成一列）。
- 组件接口是 `onLoadPath?: (set: ExampleSet) => void`：不传这个回调时，两处入口都**不渲染**——
  组件本身不假设调用方支持整条路径。会话状态与三个动作（导入 / 走进第 n 程 / 结束）都在
  `PlanPage`，组件只管显示与回调。

- **悬浮卡要写「这样规划的利弊」，不只写介绍**（2026-10-13 第三版，用户要求）：三块内容存在
  `example-paths.ts` 的 `signature` / `merits` / `limits`（中英各一份），**每条都要具体**——
  「优点」不许写「系统」「高效」这类空话，「代价与局限」必须写清哪里不能用、哪里没核对
  （例如 Rudin 那套「不能用来学内容」、梁书那套「只覆盖上册、选读小节被压缩」、
  简明高等代数那套的第一程精修范围与机器检查边界）。`tests/example-paths.test.mjs`
  会核对三块都不空、每条都不少于 10 个字。
- **悬浮卡绝不能吃掉点击**：它比一行书高得多，会盖住下面那几本。因此 `pointer-events: none`
  （点击穿到下面的按钮上），内容也随之压紧——正文 0.82rem、导语限两行、
  「特色 / 优点」两栏并排、「代价与局限」整行，实测 ≈ 560px，800px 高的窗口整块显示（限高 80vh）。
  这是踩过才知道的：中途把 `pointer-events` 改成 `auto`（想让卡片能滚），真浏览器验收立刻红在
  `<p class="example-book-intro-lead">… intercepts pointer events`——鼠标想点下面那本书，先落在卡片上。
- **缩进里的 `**强调**` 走 Markdown 渲染**（每条利弊端），否则会把星号一起漏出来。

- **上一版为什么被换掉**：那时是「置顶入口条 + 页面底部 21 张卡片」两处渲染，虽然把表单救回来了，
  但整栏仍然臃肿——用户要的是「先压缩，按学科选书」。现在卡片只在被点开的那一本下面出现。
- **悬浮简介用纯 CSS**（`.example-book-wrap:hover .example-book-intro` / `:focus-within`），
  键盘用户 Tab 到书名同样能看到。
  **窄屏没有悬浮**：手机上这一栏排在表单之后，点开书名即可看到完整导语、出处、边界说明与同一份取舍。
- **学科是量出来的，量不到才用声明值**：每套样本的学科由它自己的**里程碑节点**的 `discipline`
  现场统计（`web/src/example-paths-grouping.ts` 的 `disciplineOfSet()`），取里程碑最多的那一支作分组。
  于是「梁灿彬上册」落在「相对论与宇宙论」（31 条里程碑）而不是望文生义的「微分几何」；
  它同时覆盖的微分几何 21、拓扑 3 写在悬浮简介里。**本体比样本旧、或那一帧还没到齐时**，
  统计一个里程碑都查不到——这时用 `ExampleSet.discipline`（写在该书数据里的**声明主学科**）兜底，
  而不是显示「其他」（2026-10-13 修：用户截图里《简明高等代数》曾被归到「其他」，
  因为书单来自数据文件、分组名却只在 `nodes` 里查得到）。学科显示名与次序取自
  `case-catalog.ts` 的 `caseSectionTitle` / `SECTION_ORDER`（与案例页同一份名单；次序由组件注入，
  分组模块本身不 import 它——那样 Node 才能直接 import 这个模块来断言分组判据）。
- **短书名是数据**：`ExampleSet.shortTitle` 由 `example-paths.ts` 给出（中英各一份），
  不从 `title` 裁——中文是「作者《书名》」、英文是「Author, Title, ed.」，裁出来会一半带书名号。
- **窄屏让位给表单**：手机上这一栏排在规划表单**之后**（`useMediaQuery('(max-width: 860px)')`）——
  否则 `tests/browser.mjs` 的「窄屏规划页目标在首屏附近」会被顶出去。
- **本体没到之前不显示分类**：那时每个里程碑都查不到 `discipline`，四套样本会一起落到「其他」；
  组件改为如实显示「正在从本体读取各套样本的学科分布……」。
- **规模从数据算**：「4 套教材 · 30 程 · 219 个里程碑」不是写死的文案，加一套教材时它自己跟着变。

| 样本 | 教材 | 规模 | 节点正文 |
|---|---|---|---|
| `liang-volume-1` | 梁灿彬、周彬《微分几何入门与广义相对论》上册（第二版），10 章 / 442 页 | 七程 · 56 个里程碑 | 已写（凝练笔记） |
| `rudin-pma` | Rudin, *Principles of Mathematical Analysis*, 3rd ed.，11 章 / 355 页 | 七程 · 55 个里程碑 | **留空**（只挂名字） |
| `jiang-jdga` | 蒋剑剑、林秀清《简明高等代数》，8 章 / 正文印刷 199 页 | 七程 · 47 个里程碑 | 第一程四站及消元法已精修，其余为草稿 |
| `axler-ladr` | Axler, *Linear Algebra Done Right*, 4th ed.，9 章 / 正文印刷 382 页 | **九程**（一章一程） · 61 个里程碑 | **留空**（只挂名字） |

- **起点是累进的**：第 n 程的起点 = 基础背景 + 前面各程的全部里程碑。这条规则在 `buildPaths()` 里由代码累加，
  而不是逐程手抄一份入口清单——手抄一定会写漏，写漏了就会悄悄变成「未决入口」。
  Rudin 那套的基础背景里必须有**有限维线性代数**：第 9 章与第 10 章都以它为输入，
  少了它第六、七程直接判为界内不可行。
- **多目标**：一程要拿下好几个里程碑，只给一个目标会得到一条只服务那个节点的短路线。
  表单因此持有一组目标，请求走服务端已有的 `goalIds` 通道；单目标时请求体与改动前逐字一致。
- **数字不写死**：卡片上的「实测最短 N 个事件」由 `tests/example-paths.test.mjs` 按声明的 `horizon`
  真跑一遍规划器核对，浏览器验收还会点一次按钮、数一遍时间线上的事件数。
- **起点不藏在网格里**：「可用背景」网格只列没有任何行动能产出的节点，而范例的起点大多是前几程的成果。
  载入范例时这些声明会单独列全——否则会出现「背景是空的却规划出了路线」这种误导。

#### 从零走一遍（可复跑）（2026-10-13）

范例卡片是「一程一程点」的入口；想**从头到尾走一遍**用脚本：

```bash
pwsh -File scripts/start.ps1 -NoBrowser   # 起本机服务（默认 127.0.0.1:3784）
npm run walk:examples                     # 走《简明高等代数》七程，生成 docs/从零走一遍-jiang-jdga.md
```

`scripts/walk-example-path.mjs` 全程走真接口：建一份 `blank` 档案（一个已确认节点都不预设）→
只确认范例声明的起点 → 逐程 `POST /api/v2/plans?sync=1`（**背景由服务端从档案的确认记录派生**，
脚本不传背景清单）→ 把这一程实际产出的节点逐条确认 → 下一程。因此「起点 = 基础背景 + 前几程里程碑」
这条规则是被**档案状态**验证的，不是脚本假设的。实测：七程各 4/7/7/6/5/8/10 个事件，
累计已确认 6 → 13 → 20 → 26 → 31 → 39 → 49。

三件顺带量出来的事，写在 [从零走一遍-jiang-jdga.md](docs/从零走一遍-jiang-jdga.md) 里：

- **为什么必须分七程**：`horizon` 上限是 32，全书 47 步。h=32 实测——前五程（29 个目标）`Found`（29 个事件），
  前六程（37）与全部七程（47）都是 `InfeasibleWithinBound`。
- **站内判据的收尾证明**：走完后用同一份「学习方案」偏好（主目标 = 奇异值分解）重算，`primaryComplete` 变成 `true`。
  从零时它是 `Conditional`、里程碑「行列式的定义」、8 步。
- **走完七程还剩什么**：47 个里程碑之外，案例里那 4 个**方法节点**（Gauss 消元法、配方法、辗转相除法、
  归约到标准形）不在这条路线上，档案里仍然未确认——「我的学习」页面把它们列成「现在可以新学」。

脚本参数：`--set <id>`（默认 `jiang-jdga`，也可 `rudin-pma` / `liang-volume-1` / `axler-ladr`）、`--base <url>`、
`--reuse`（复用同名档案重跑；已走完的程如实记 0 事件）、`--no-profile`（不建档案、背景显式传，对照用）、
`--out <文件>`。它写的是 **E 层**（一份新档案的确认事件），不碰公共本体 M。

**第二套走通记录（2026-10-14）**：同一脚本走 **Axler 那套九程**，产出
[从零走一遍-axler-ladr.md](docs/从零走一遍-axler-ladr.md)——九程各 6/5/10/4/9/7/9/6/5 个事件、

## 点集拓扑案例（第八个案例，2026-10）

需求是一份**点名清单**：为网站设计以下节点——拓扑空间、可数公理、分离公理、同胚、紧、仿紧、
σ-紧、连通性、拓扑流形、微分流形、坐标卡、图册。本案例把这 12 项做成 12 个**单元级**概念节点，

### 为什么新建而不是复用既有登记

这 12 个名词在本站原有**三种深度的登记**，但都不是「单元级的点集拓扑」：

| 已有 | 是什么 | 缺什么 |
|---|---|---|
| `bg:top:space` | 背景**接口**（把拓扑空间与局部欧氏性合成一个最低接口） | 粒度是接口粒度；它的 `boundary` 自己写着「一般拓扑的分离公理与紧性理论未在本站展开」 |

| `manifold:top-manifold` | 专稿案例 02 的拓扑流形 | 与 dg 的版本互相独立登记，缺一条说明「三处差别」的关系 |

因此本案例的做法是**新建**，不改名、不覆盖、不合并既有节点；三处登记用 `crossDomain` 关系互指，

## 同一对象的多处登记：合并（2026-10）

**要求**：用户的原话是「有很多重复名字或话题高度重合的节点，合并它们」。当时的账是这样：
节点列表里出现三个「拓扑空间」、三个「紧致性」、两到三个「度量空间」「同胚」「微分形式」
「Stokes 定理」，网络视图里同一个对象分成两三个点——读者看到的是**登记方式**，不是数学。

**做法**：登记本身不动（`data/cases/*.mjs` 一个字没删），在**装配期**把同一对象的多处登记
收成一个规范节点。合并表在 [`data/merges.mjs`](data/merges.mjs)：29 组、吸收 38 处登记，
节点数 269 → 231，而**登记总数一处没少**（每一处都逐字挂在规范节点的 `registrations` 上）。

| `dg:topological-manifold`、`dg:manifold`、`manifold:top-manifold` | `top:topological-manifold` | **公理表故意不同**：dg 版不含第二可数 |

| `rudin:metric-space`、`top:metric-space` | `dg:metric-space` | top 版原先只是本案例的辅助前置 |
| `dg:d-squared-zero` | `dg:claim-d-squared-zero` | 同一结论的概念版与断言版 |
| …（其余见合并表） | | |

### 四条不变量（`tests/merge-consistency.mjs` 逐条钉住）

1. **身份唯一**：被合并的 id 不再是节点，但**别名仍然解析得到规范节点**——
   `/nodes/dg:topological-manifold` 这类旧链接不 404，页面顶部写明「已合并到 `top:topological-manifold`」。
2. **内容不丢**：每一处登记的标题、案例、形式负载、来源与**正文块**都保留；
   节点页在「合并前的其它登记」里把它们连同 LaTeX 形式表达一起排版出来。
3. **差别不抹平**：每一组都逐条写着各处登记的差别（拓扑流形那条最要紧：含不含第二可数）。
   合并收的是身份，不是数学。
4. **改写到底**：关系端点、行动输入输出、证据、支持集、断言、误区锚点、聚合成员、
   节点内部锚点里都再也找不到被合并 id；本体校验与 `npm run check` 各有一条断言盯着。

### 三条已知后果（不是缺陷，是取舍）

- **案例线按「登记归属」筛**：规范节点的 `cases` 是「自身案例 ∪ 各处登记的案例」的并集。
  节点列表、网络视图与首页案例卡片的案例筛选都按它走，因此微分几何案例仍是 35 处登记，
  不会因为收口而凭空瘦一圈。节点归属（`node.case`）与登记归属（`node.cases`）从此是两件事。
- **硬前置取并集**：同一对象在两处登记的前置不同时，合并后的节点要同时满足两套
  （判据从「同一个 `case` 前缀」放宽成「两个端点共享至少一个登记案例」，
  `tests/hard-prereq.mjs` 按新口径核对）。直接的可见后果是：原先「有行动、没登记输入」
  的那两个 dg 节点（拓扑空间、度量空间）现在带着 top 案例登记的前置，空白档案下
  起始节点只剩背景接口（`tests/starting-nodes.test.mjs` 把这条写成断言）。
- **引入路径取并集（OR）**：同一对象的几条引入契约都还在，任一条走得通就能引入它；
  `limit:limit-ed` 因此多了一条经由 `dg:metric-space` 的路径（`tests/core.test.mjs` 记了这件事）。

### 明确**不**合并的（`KEPT_SEPARATE`，逐条写着理由）

`bg:*` 背景接口与同名的单元级节点（不同层）、切向量的曲线定义与导子定义（同一对象的两种构造）、

- **全屏模式**：HUD 的「全屏」按钮把画布置为 `position: fixed` 并请求浏览器全屏，`Esc` 退出后按钮文案自动复位。
- **平移与缩放**：拖动空白处平移，滚轮以光标为锚点缩放（25%–300%），HUD 显示当前比例。「重置」= 把整张网络**适配**进可见区，不是回到 100%——网络常比视口大，1:1 会把内容裁到视口外。加入节点后自动适配一次，但不会覆盖手动缩放。
- **触屏上的双指缩放（2026-10-05）**：两指距离之比就是缩放比，两指中点是不动点（中点下的那个世界点全程不动），两指整体移动同时平移——缩放与平移是同一个式子，不是两条会互相打架的路径。画布本来就 `touch-action: none`（平移需要），所以浏览器原生缩放不会来抢；手势由 pointer 事件自己实现，落在节点上的那根手指也照样参与（第二根手指一落就把手势接管过来，同时作废节点拖动与长按选择器）。手势结束后剩下的那根手指接着当平移用，不必把手全抬起来重按。
- **窄屏的相机坐标系（2026-10-05 修）**：`viewBox` 与相机几何一律按**画布元素**量，而不是按 `stage`。窄屏（≤860px）画布只是 stage 里一块 `46vh` 的框，而 stage 有整页那么高——按 stage 写 viewBox，`preserveAspectRatio` 会把整张图再缩进那块框：手机实测 CTM 只有 **0.1487**、节点 28×10px、网络挤在画布左边一条 58px 宽的带子里。改后 CTM ≈ 0.99、节点 188×64px；桌面端画布本来就铺满 stage，取值完全不变（`tests/network-camera.mjs` 等六套网络验收一条没动）。

### 七类连接（这就是「连接太少」的修法）

可用的连接依据一共七类，**默认只画「行动契约 + 登记关系」**：这两类是本里真正声明过的依赖与语义关系。
其余五类是辅助线索，在「连接类型」面板里逐类打开（开关上显示当前条数）——七类全开时连线会把节点卡片压成小字，
因此默认收敛，想看密度时再开。全库数据本身支持七类边：

| 类型 | 依据 | 全库边数 |
|---|---|---|
| 行动契约 | 产出该节点需要哪些输入 | 168 |
| 登记关系 | 语义关系（种类 + 见证状态 + scope） | 32 |
| 同一话题 | 同属一个聚合话题块 | 193 |
| 误区锚点 | 误区模式的节点与锚点 | 22 |
| 共用前提 | 同一行动的两个输入 | 59 |
| 同一份证据 | 同一份证据记录同时引用的节点 | 14 |
| 支持族依赖 | 节点在支持族里列出的依赖（含传递依赖） | 65 |

效果（全库 102 节点）：

| | 平均连接数 | 中位连接数 | 度数 1–2 的节点 | 孤立节点 |
|---|---|---|---|---|
| 改前（2 类） | 3.43 | 3 | 31 | 2 |
| 改后（7 类） | **6.49** | **7** | **26** | **1** |

每个节点卡片右上角**直接标出它的连接数**，详情面板也写明「连接 N 条」；连不上时明确说明原因，而不是留一片空白。

**每一类都能追到已登记数据**，没有一类是编出来的：`同一份证据` 明确标注「这是『一起被论证』，不是因果」；`支持族依赖` 标注「比行动契约更宽，包含传递依赖」。HUD 的「连接类型」面板可逐类开关并显示当前条数——关掉一类边数立刻下降，验证开关真的生效。

### 推荐理由的强弱顺序

1. **图中前提已加入**——某个产出它的行动，全部输入都已在**这张图**里（依据：行动契约）。
   措辞刻意不含「掌握」：它说的是视图已经具备条件，不是学习者已经会了。
2. **已有登记关系**——与已加入节点之间存在登记关系，附关系种类、见证状态与 `scope` 原文。
3. **共用前提**——与已加入节点共享输入，并列出还缺哪些输入。
4. **同一话题**——同属一个 `aggregate` 话题块（话题允许重叠，不构成必修关系）。
5. **误区锚点**——某误区模式的锚点，且该模式已有锚点加入。

网络为空时给的是**起始节点**（2026-10 起；面板标题也从「起点推荐」改成「起始节点」）：
一类是没有任何行动能产出的背景接口（只能由学习者先确认），另一类是**当前档案里前置已确认**的节点
——两者都由 `web/src/starting-nodes.ts` 派生，条目上标「起始」。判据见「起始节点与默认档案模板」一节。
**同轮改掉一处口径**：从前这一档只按 `case === 'background'` 筛，于是 `bg:misc:counterexample-method`
（`case: 'background'`，但另有一条引入契约）被推成「背景起点：没有任何行动能产出它」——那句话对它是假的；
现在它必须真的没有产出行动才会出现在这一档。

**明确不做**：不给出认知成本、难度或学习时长（全仓没有这类字段）；不给不存在的 `hardPrereq` 编实例（只登记能指名「依据在定义哪一处」的那 103 条，见「硬前置关系」一节）；与当前网络无登记连接的节点放入「未连接」，如实说明，不替它编一条边——**「无关系」本身有分类**（背景接口 / 线索层 / 由契约引入 / 尚待登记 / 完全孤立），见 README 的「无关系节点的分类」与 `data/relation-coverage.mjs`。

### 早期网格排布的取舍（历史方案）

试过用力导向直接决定位置，**不行**：13 节点 78 条边时原始输出 1724×919 里有 **48 对卡片重叠**，关系全被遮住。也试过「二分搜索一个放大系数把节点拉开」，结果坐标爆到 45000×51800，图彻底不可用——那是治标，重叠的根源是相对位置错，等比放大只会把错误放大。

当时改成**结构化网格**：先按力导向的 y 排序，再依次填格，以连续位置换取卡片间距。
这段保留早期取舍；**当前实现已改为力导向 + `relaxToSpacing` 间距松弛**，见下文「布局是力导向」及
`web/src/network.ts` 的 `layout()` / `attractionOf()`。权重参与吸引计算，不保证最终边长随权重单调排序；
多个邻居、斥力与避让会共同影响结果。原网格描述不能继续作为当前实现的依据。

### 相机模型

`viewBox` 恒等于画布像素尺寸，相机放在 `<g transform="translate(...) scale(...)">` 上，即 `screen = world × scale + offset`。这样做是因为旧实现把「可用区算出的比例」塞进覆盖整个画布的 viewBox、再由 `preserveAspectRatio` 二次缩放，实际比例与名义比例不符，「以光标为锚点」的公式因此算错——表现就是放大时内容往左上角飞。现在 `scale` 就是真实比例。

- **滚动缩放**：以光标为锚点（用 `svg.getScreenCTM().inverse()` 换算，不手算 `clientX - rect.left`）。连续放大 4 格的累计漂移 < 1px。
- 倍率按 `deltaY` 归一化为 `exp(-delta*0.0015)`，限幅 ±15%/次——固定倍率在触控板上会瞬间冲到上下限。
- **拖动平移**：拖多少走多少。
- **重置**：把整张网络适配进可用区并居中（用节点的真实包围盒，不是含外边距的布局盒），不是回到 100%。

布局**只依赖「已加入集合 + 边源」**，不依赖面板占用或窗口尺寸——这两个都是测量值，在加载过程中会变，一旦参与布局，同一 URL 刷新前后就会得到不同坐标（实测差 83px，正好一行间距）。

### 关系可视化条款：越硬越重

**先说一个容易误解的事实**：图例里关系种类不少，但画布上常常几乎看不到——因为**本体里登记的语义关系本来就少**（全局 32 条，关系最密的那 14 个节点里只有 3 条）。所以「看不到关系」通常不是画漏了，而是语义关系确实稀疏。

**2026-10 修正：行动契约按 `mode` 分档。** 原先契约一律按「结构骨架」压到最弱一档
（0.18 → 1.1px、0.34 不透明、细虚线、不标名称），而本体把最硬的依赖全登记在契约里——
全库 216 条契约中 `definition` 85 条、`deduction` 61 条；`hardPrereq` 关系在 2026-10 之前**一条都没有**，
现在按定义与推导登记了 103 条（见「硬前置关系」一节）。
于是「同胚 → 流形」（`a-dg:manifold` 的 definition 输入）被画得比 `crossDomain` 还轻。
现在：

| 契约 mode | 权重 | 档位 | 画法 |
|---|---|---|---|
| `definition` 定义性前置 | 0.9 | 核心断言 | 4.97px 实线、满不透明、标「定义性前置：<行动标题>」 |
| `deduction` 推导前置 | 0.5 | 结构性关系 | 实线、标注 |
| `construction` / `method` / `task` / `evidence` / `representation` | 0.16–0.2 | 行动骨架 / 登记关联 | 细虚线、不标注 |

不变量重写为三条：任何语义关系 > 任何结构关联；任何语义依赖 > 任何结构关联；
定义性前置 ≤ 硬前置且 > 最弱语义关系。**结构关联的上界包含所有非语义 mode 的权重**
（第一版漏了这一点，被 `tests/relation-visual.test.mjs` 当场抓出）。

即便如此，渲染必须让已有的关系跳出来。做法是把每一类关系映射到 **0–1 的视觉权重**，再由权重统一推出线宽、不透明度、线型、饱和度与是否标注。规则、依据与逐档参数写在站内「关系可视化条款」面板里（网络页 HUD 打开），源码在 [`web/src/relation-visual.ts`](web/src/relation-visual.ts)。

三条依据都能在公共本体里核对：

| 依据 | 内容 |
|---|---|
| 关系种类强度 | `hardPrereq` 1.0 > `scaling` 0.95 > `application` 0.72 > `crossDomain` 0.68 > `duality` 0.62 > `bridge` 0.56 > `analogy` 0.4 |
| 见证状态 | `PROOF` 1.0 > `FINITE` 0.95 > `DEF` 0.82 > `REF` 0.7 > `ILLUSTRATION` 0.62 > `NOT-CLAIMED` 0.6 |
| 边源家族 | 契约 0.18 > 共用前提 0.13 > 支持依赖 0.11 > 同一证据 0.09 > 误区锚点 0.08 > 同一话题 0.05 |

五档视觉参数：

| 层级 | 线宽 | 不透明度 | 线型 | 标注文字 |
|---|---|---|---|---|
| 核心断言（不满足就不成立，带 PROOF） | 4.6 | 1.0 | 实线 | 是 |
| 强关系（应用 / 跨域 / 对偶） | 3.2 | 0.95 | 实线 | 是 |
| 结构性关系（桥接 / 类比） | 2.2 | 0.85 | 虚线 | 是 |
| 行动骨架（行动契约） | 1.7 | 0.6 | 虚线 | 否 |
| 登记关联（同话题 / 共用前提 / 同一证据 / 支持依赖） | 1.1 | 0.34 | 细虚线 | 否 |

**硬性不变量**：任何语义关系都必须强于任何结构关联，用**最弱见证**检验（`assertHierarchyHolds()`，在 `npm test` 里跑）。写这条断言时它立刻抓出一个矛盾——`analogy` 在 `NOT-CLAIMED` 下只有 0.2，而契约当时是 0.34，规范与数值自相矛盾；于是把契约压到 0.18。

两处容易搞错的细节：

- **方向性由边源决定，不由权重决定**。契约（前提 → 产出）与语义关系有向、给箭头；「登记关联」五类是无向的同组关系，刻意不给箭头。曾把箭头挂在权重档位上，结果契约边丢了箭头——方向信息被样式规则吃掉了。
- **提饱和只动饱和度**，不动色相与明度：色相承载「哪一种关系」，明度承载可读性。

### 放缩关系的箭头「一头粗一头细」（2026-10-11 加）

用户的要求：「给表达放缩关系的箭头进行视觉优化：增加粗细变化，**泛化方向变粗，特化方向变细**。」

SVG 的 `stroke-width` 是常数，描边画不出一头粗一头细，因此放缩边改成**实心带子**：
[`edge-routing.ts`](web/src/edge-routing.ts) 的 `taperedOutline` 沿同一条曲线采样、每点沿法线偏移「该处的半宽」，
首尾闭合成一个可填充轮廓；原来的 `<path>` 保留全部 DOM 契约（`d` 仍是那条曲线、`stroke` 仍是关系色、
`stroke-width` 仍是本档线宽、`marker-end` 仍在这一条上），只把**描边本身**藏起来（`stroke-opacity: 0`）——
箭头由它的 marker 渲染（浏览器里实测过：`stroke-opacity: 0` 时只剩箭头那 48 个像素）。
带子画在主路径**之前**，于是箭头压在带子之上；新边的淡入复用既有的 `network-edge-fade`（不新增 `@keyframes`）。

- **倍数按本档线宽算**（[`relation-visual.ts`](web/src/relation-visual.ts) 的 `SCALING_TAPER`）：一般端 ×2.2、特殊端 ×0.5。
  放缩关系落在 core（实测 5.01px）与 strong（3.38 / 3.31px）两档 → 一般端约 11.0px、特殊端约 2.5px。
  用倍数而不是绝对像素，是因为线宽已经承载「关系强度 × 见证状态」这层信息；粗细只表达**这条边内部的方向**，
  不该覆盖强弱——`strong` 档的一般端仍粗于 `core` 档的特殊端，这一条有断言。
- **细端必须同时换小箭头，否则白改**（2026-10-11 用户报「还是两头一样粗」之后的修正）：
  箭头是**固定像素**的（档位箭头在 core 档横向 10.1px），第一版只有 1.6× 的一般端（8.0px）**比箭头还窄**，
  于是「细的那端」被箭头重新撑粗，两端看起来一样。现在两头一起改：一般端 11.0px 明显宽于箭头，
  细端配一支**更细长的专用箭头**（`TAPER_ARROW_PATH`，`markerWidth` 6、横向 2.0px），
  两端**看得见的**宽度比因此是 4.4:1。验收里专门有一条把箭头算进去量「两端看得见的宽度」，
  以及一条「细端用的是 `-taper` 专用箭头」——只验带子几何（8.0 vs 3.0）抓不到这个 bug。
- **方向由数据决定，不按 `from`/`to` 猜**：`direction.reading` 有两种朝向（`contract` = 一般→特殊、`expand` = 特殊→一般），
  实测 14 条有方向的放缩关系里**各占一半**。服务器用 `shared/scaling.mjs` 的 `scalingEndpoints` 解析后随图接口下发
  （`relations[].scaling = { general, special }`），前端只读结果——前端不引 `shared/*.mjs`，两边各写一份判据迟早会漂。
- **不知道方向的记录不做变化**：11 条旧记录（`scalingMode: unresolved`）下发 `scaling: null`，
  渲染保持原来的等宽线，不假装知道哪端是泛化端。
- **档位带虚线时也不做变化**：填充形状画不出虚线，宁可不改也不丢线型（放缩关系当前都在实线的两档，因此实际都画带子）。
- 验收：`tests/edge-routing.test.mjs`（带子几何：两端宽度、中点线性过渡、与曲线逐点重合、确定性）、
  `tests/relation-visual.test.mjs`（倍数与「不覆盖档位强弱」）、`tests/api.test.mjs`（图接口下发的方向：两种读法、未核验为 null、非放缩不带字段）、
  `tests/network-edges.mjs`（画布：只有放缩边有带子、粗端落在泛化端、带子与线同锚点、**两端看得见的宽度比 ≥2 且细端用专用小箭头**、描边藏起来但属性照旧）。

### 颜色与遮挡（2026-10 修正：这里原来有两个实现错误）

**颜色分两路**：语义关系按 `kind`（`RELATION_COLOR`）、行动契约按 `mode`（`CONTRACT_MODE_COLOR`）。
契约是全库最多的一类边（386 条），旧版**全部共用中性灰**，于是画布上绝大多数线是同一团灰。
调色板有硬规则并有测试：种类齐全、颜色不重复、**同族色相间距 ≥8°**、明度落在 0.2–0.6、饱和度 ≥0.25
（`analogy` 是**故意的中性灰**，单独豁免）；饱和度**分层**——语义关系 1.5、语义契约 1.2、结构骨架 1.0
（契约数量多，再提会把整块画布染成一种电紫）。跨族允许色相接近：关系与契约已由线型、线宽、标签与图例分开。

**箭头必须显式给 `fill`，尺寸必须固定像素**。旧版三个共享 `<marker>` 的 `<path>` 没写 `fill`
→ 继承默认填充 = **纯黑**；`markerUnits` 默认按 `strokeWidth` 缩放 → 4.97px 的粗线配 9 单位箭头约 **45px**。
这就是「全都是大黑箭头」的成因。现在**一种颜色一个 marker**（id 里带着颜色，验收据此核对），
`markerUnits="userSpaceOnUse"` 固定像素（13 / 10.5 / 8.5 三档）。

**遮挡按逻辑强弱**：按视觉权重**升序**排序后渲染，最强的边最后画、压在最上面；
与选中节点相连的边再提到最后。旧代码算过一个三档 `order` 并注释「硬关系压在软关系上面」，
但 `order` 只被写进 `<desc>`、从未参与排序——那句话在代码里是假的。边另有 `data-from`/`data-to`，
验收才能精确判定「末尾那几条是不是相连的边」。见 `tests/network-edges.mjs`（27 项，含放缩箭头粗细变化那 8 项）。

### 同一对节点只画一条（合并显示，`mergeParallelEdges`）

本体里同一对节点常同时有「行动契约」与「登记关系」（`拓扑空间 → 流形` 既有 definition 契约、
又有 hardPrereq），**第二十九轮**的问题就是这种情形会叠两条线。规则（`web/src/network.ts`）：

1. 按**无序对**分组（A→B 与 B→A 算同一对）；
2. 留**视觉权重最大**的那条（与线宽、吸力同一把尺子 `visualWeightOf`）；
3. 权重相同看边源：`relation` > `contract` > 族边；
4. 再相同按 `id` 字典序（结果与输入顺序无关）；
5. 其余边**不丢**：标签后标 `+N`，提示里逐条列出它们是什么、各重多少。

HUD 会写「63 条边（另有 34 条同对边并进这些线里）」——画布上少画的线必须有交代。
**布局的吸力、度数统计与推荐理由仍按完整边集算**：合并只影响画，不偷偷改图的形状。
效果（实测）：dg 整案 97 → 63 条、liang 整案 130 → 110 条、全库 545 → 436 条。
验收：`tests/edge-merge.test.mjs`（6 项，规则五条 + 真实数据）与 `tests/network-edges.mjs`（界面照做）。

### 绕不开的关系改走弧线（`web/src/edge-routing.ts`）

弧线是**补救手段，不是风格**：只有「绕不开」的情形才给边一个弓高，其余一律保持直线。

| 情形 | 判据 | 处理 |
|---|---|---|
| **平行边** | 同一对节点之间有多条边（直线必然完全重合） | 对称弓高（三条 → −18 / 0 / +18），并**沿卡片边缘散开进出锚点**。合并显示之后界面不会再产生这种边，代码保留给不合并的调用方 |
| **穿卡** | 直线在 t∈[0.15, 0.85] 内压住第三张卡片 | **第二版（2026-10）**：由每张挡路卡反解出候选弓高（正负两侧、再加几档余量与大弓高），逐个验「这条曲线还压着几张卡」，只在**压卡数严格更少**时采用；一样多就保持直线。上限 96px |
| **共线重叠** | 与前面的边 \|cos\| ≥ 0.97 且中点横向距离 < 10px | 往更远的一侧挪，复验，最多八步 |

第一版穿卡是「取最苛刻的一张卡、按它算一个弓高」，实测**弯了还是压卡**：同一张图上可能左右两侧
都有挡路卡，按一侧弯过去正好撞进另一侧；弓高一旦被上限截断也没有第二次机会。
现在的做法保证「**弯过的边一定比直线压得少**」，但**不保证清空**——密排视图里可能存在
任何弓高都绕不开的边，那种情形如实计入 `stats.throughCardResidual`，
HUD 与条款面板都写出来（「N 条边仍压着卡片（弓高上限 96px 内无解）」）。
实测：liang 整案 110 条边里 31 条因压卡而弯、16 条仍压着卡片；全库 436 条里 133 条弯、162 条仍压着。

两个踩过的坑写在这里：**弓高要按「世界侧」而不是「各自法线」统一**——同一对节点的边可能一条写成 A→B、
另一条写成 B→A，各按自己的法向翻符号会把两个不同的对称值映到同一侧（实测 `[18, 0, 18]` 仍重合）；
**平行边必须散开锚点**——共用卡片中点会让几条弧线在边缘挤成一个点，比直线更乱。
渲染上边统一用 `<path d="M … Q …">`，标签落在曲线顶点（顶点偏移 = 控制点偏移的一半）。
验收见 `tests/edge-routing.test.mjs`（8 项：三种情形 + 上限内无解时保持直线 + 上限与确定性）
与 `tests/network-edges.mjs`（有解的视图必须 0 条压卡；密集视图的残余不得超过页面报告的数）。

### 硬前置关系（2026-10 起不再是空的）

`hardPrereq` 说的是「**不用它就推不下去 / 定义不出来**」，是全库最强的一类关系。此前它一条都没有，

| 微分几何（`dg`） | 36 | 拓扑空间 → 同胚 / 流形 / 紧致 → 坐标图 → 图册 → 光滑结构 → 切向量 → 切丛 → 微分形式 → Stokes |
| 流形（`manifold`） | 9 | 背景拓扑 → 拓扑流形 → 图册 → 过渡映射 / C^k → 光滑 → 兼容 → 最大扩张；证书 → 目标断言 |
| 张量（`tensor`） | 10 | 线性代数背景 → 对偶 → 多重线性 → 张量积 → (r,s) 型 → 换基规律 / 张量丛 → 张量场；证书 → 目标断言 |

- 方向一律「前置 → 依赖它的对象」：拓扑空间 → 同胚、同胚 → 流形、坐标图 → 光滑图册、切丛 → 微分形式…；
- 每条写两层依据：`witness.scope`（出现在目标节点定义/陈述的哪一处）与 `scope`（这条依赖说的是什么）；
- **两种见证类型**（2026-10 起可区分，校验器强制）：

  | 见证 | 含义 | 登记要求 |
  |---|---|---|
  | `definitional-dependency` + `DEF` | 不用它，目标节点的**定义或陈述**就写不出来 | `witness.scope` 指明定义里的哪一处 |
  | `proof-dependency` + `PROOF`/`FINITE` + `ref` | 目标的**论证**用到它 | `ref` 必须指向一条**同时列出两端节点**的证据记录；见证状态必须与证据的 `status` 一致 |

  第二类让「某定理用到另一条定理」变成可核的：例如 `dg:inverse-function-theorem → dg:implicit-function-theorem`
  指向 `ev-dg-inverse-implicit`，`rudin` 的两条指向 `ev-rudin-inverse-from-contraction`
  与 `ev-rudin-implicit-from-inverse`，四个证书片段指向各自的机器证书记录。
- 只登记核心链，**不登记**例子、误区、方法、练习类节点之间的一般联系（那些由契约与证据承担）。
- 背景节点（`bg:`）可以作为前置的**来源**（背景存在的意义就是当前置），但不作为目标。

#### 一条登记纪律：不要靠「两条反向边」表达双向关系（2026-10 加）

画布上，同一对节点之间的多条边会被 `mergeParallelEdges` 合并成**一条**（保留视觉权重最高的那条，
其余条数写在标签后的 `+N` 里，悬停可看全部）。这条渲染规则有一个不显眼的后果：

> **A→B 与 B→A 也算「同一对节点」**，于是反向的那条会被合并掉，**箭头方向只剩下一个**。

点集拓扑案例重审关系时踩到过：`topological-manifold ↔ differentiable-manifold` 一度同时登记了
`scaling` 的放、缩方向记录，视图里只画一条——读者看到的是「少了一条关系」。
所以现在的口径是：

1. 双向的信息**写进同一条边的 `scope`**（例如「反向不成立，因为同一个拓扑流形上可以有不兼容的 C^r 结构」），
   而不是登记两条反向边；
2. 同一对节点之间**只留一条**边（`data/cases/top.mjs` 的装配前自检会报「同一对节点登记了 N 条关系」）；
3. 真有两条**依据不同**的边（例如「陈述材料」与「传播定理」），必须在 `scope` 里写明「为什么不并」，
   并且把它们放在同一对节点的**同一方向**上，不要一正一反。


规则层同时加了一条：**`hardPrereq` + `DEF` 见证不打折**（`witnessFactorOf`）。
否则它的渲染权重是 1.0 × 0.82 = 0.82，比定义性前置契约的 0.9 还轻——「不满足就不成立」反而
画得比从行动接口推出来的契约更淡，最高一档里依旧只剩契约。其它种类、其它见证照旧打折
（`proof-dependency` 的 `FINITE` 档是 0.95，仍在 `core` 档内）。
`assertHierarchyHolds()` 的不变量 D 把这条钉住：以定义为见证的硬前置必须 ≥ 定义性前置，且必须落在 `core` 档。

验收：`tests/hard-prereq.mjs`（条数、案例范围、端点存在、见证与依据、无重复、tier 为 core、不变量、
证明依赖的两端可核）与 `tests/network-edges.mjs` 里的两条渲染断言（画布上出现硬前置且落在最高档、
不比起定义性前置细）。

### 无关系节点的分类（`data/relation-coverage.mjs`）

本体里有一百多个节点**不作为任何语义关系的端点**。这不一定是缺口——关系不是唯一的表达方式
（行动契约、证据、支持族都在表达依赖），但「不连」必须能分类，否则读者分不清「设计如此」与「忘了登记」。
分类由**规则 + 一份显式待办清单**给出（不写死节点名单），`npm run check` 与
`tests/relation-coverage.test.mjs` 会核对：

| 类 | 含义 |
|---|---|
| 背景接口（`bg:`） | 环境边界的声明：按设计只在契约与边界引用里出现；其中 4 个另有一条「背景 → 案例核心」的硬前置 |
| 线索层（话题级条目） | 一条学习线索的名字，不是可独立认知的单元：网络里单独成层、不参与前置计算 |
| 由契约引入 | 方法、练习、例子、反例、误区与证书片段：与对象的联系写在契约的输入输出里，再补一条语义关系只会重复 |
| **尚待登记** | 单元级的概念 / 断言 / 构造：理应有一条语义关系（定义性依赖或推导依赖），目前只有契约。清单逐条写明「欠什么」 |
| **完全孤立**（缺陷） | 既不是任何关系的端点，也不是任何契约的输入或输出——必须为 0 |

当前计数由 `npm run check` 的 `[6] 无关系节点的清单与分类` 现场打印（数字不写死在文档里）。
2026-10 这一轮把第 5 类清零（给背景侧唯一那个孤立的方法节点补了 `mode=method` 的引入契约），
并把第 4 类压到三十余条（五个案例的定义链与推导依赖已补登记）。

### 保存的视图（2026-10 新增：下次可以直接用）

用户的要求：「在知识网络里面加入保存功能，下次可以直接用。」

**保存什么**：把当前的网络状态打包成一条**带名字的视图**——四样一起存、一起还：

| 存的 | 还到哪 |
|---|---|
| 已加入的节点 id 列表 | 画布上的节点集合（同时写回 `?nodes=`） |
| 可见边源（七类里开了哪几类） | 「连接类型」的开关状态 |
| 手动位置（拖过的节点坐标） | 覆盖到网格布局之上（与拖动同一层） |
| 相机（中心 + 缩放） | 视角原样回去 |

**存在哪里**：选了学习者档案就存 **E 层**（`network_views` 表，跟着档案走、随档案导出、跨浏览器）；
**没选档案**就没地方落 E，于是退回本机 `localStorage`（键 `mcs-network-views-local-v1`），
且面板上**如实写出当前存在哪**（「存在学习者档案（E）里」／「未选择学习档案：视图存在这台浏览器里」）。
两种来源在列表项上也标了「档案（E）／本机」。

**本机视图存入档案（2026-10-07）**：选择档案后，打开「视图列表」，会显示本机待迁移数量与目标档案名。
点击「存入当前档案」后逐条保存、回读核对，再移除对应本机副本；中途失败会保留未确认的记录，允许重试。
已经存在的同名同内容快照不重复创建，同名但不同内容的视图分别保留。迁移中切换档案会停止后续操作；
本机记录损坏或存储不可用时明确报错。所有档案视图写请求统一经过带 CSRF 令牌的 API 客户端。

**查找视图（2026-10-08）**：视图列表支持按名称搜索（忽略首尾空格及英文大小写），按最近/最早更新、
节点数量或名称排序。空结果可以清除搜索，同名视图有分别编号的提示，结合节点数和更新时间区分；
搜索、排序和编号仅影响显示，不重命名、不覆盖原记录。切换学习档案时重置查询和排序。

**快照边界**：一条视图是独立快照，载入替换当前画布，不自动合并。相机在保存时固定，后续拖动/缩放
不改写已保存记录；再次保存会新增快照。这个边界会在面板和保存回执中说明，未新增自动保存或覆盖更新。

**只写 E，不碰 M**：保存与载入都不改本体——验收里专门断言「保存后本体版本哈希不变」，
并且**不产生学习事件**（保存视图不是学习行为，不该出现在事件流里）。载入若发现保存时的节点
已不在当前本体里，**如实说出跳过了几个**，不静默替换。接口：
`GET/POST /api/v2/profiles/:id/network-views`、`PATCH/DELETE …/network-views/:viewId`；
服务端用本体核对节点 id 与边源，未知的直接拒绝（400），不静默丢弃。

**实现细节**：`server/db.mjs` 里那张表是**附加式 DDL**——`SCHEMA_VERSION` 不跟着升。
版本号在 `db.mjs` 里是被严格比对的，升它会把已有数据库整个判成「不兼容」；只有破坏性变更才该那样做。
`normalizeNetworkView`（`shared/contracts.mjs`）管形状与范围，`server/api.mjs` 的 `checkViewPayload` 管
「节点是否真在本体里」。验收见 `tests/network-views.mjs`（含断线重试、同名快照、中英界面与窄屏）
及 `tests/https-public.mjs`（HTTPS 公网模式下真实浏览器的保存、改名、删除与迁移）。

### 检索的排序：命中之后按相关性，不按 id（2026-10-12 修）

**用户报的**：在「全部节点」面板里搜「紧」，前几条是「广义 Stokes 定理」「单位分解」，
真正相关的「连续性与紧致性」排在后面——看起来像筛选坏了。

**其实不是筛选错，是排序错**。检索一直在四个字段上做子串匹配
（`id` / 标题 / 摘要 / 别名），命中之后却按 **`id` 的字典序**排。于是「紧」字出现在**摘要**里
（广义 Stokes 定理的摘要讲紧支撑）的节点抢在标题就叫「紧致性」的节点前面。

规则收在 [`shared/search-rank.mjs`](shared/search-rank.mjs) 一处（**服务端**
`/ontology/nodes?q=` 用它），前端「全部节点」面板用等价实现
[`web/src/search-rank.ts`](web/src/search-rank.ts)——前端不能引 `shared/*.mjs`
（见 `web/src/i18n/locales.ts` 文件头的说明），因此等价性由
`tests/search-rank.test.mjs` 的「两处逐字一致」断言守着。

| 顺序 | 特征 | 分档 |
|---|---|---|
| 1 | **命中字段** | 标题 1000 > 别名 700 > id 400 > **只有摘要命中 −350** |
| 2 | **命中完整度** | 整串相等 +100 > 从头匹配 +50 > 子串 +0 |
| 3 | **命中位置** | −min(位置, 60)；**id 命中另扣 30/次** |
| 4 | **连续性** | 逐字相邻 +16/对（上限 48）——「紧致性」赢过「紧…致」 |
| 5 | 并列 | 按 id 字典序（**确定性**，两次调用逐字相同） |

三条同时改掉的相邻缺陷：

- **排序在截断之前**：以前是 `filter(...).slice(0, limit)`，被砍掉的是「id 最靠后的那些」，
  搜出来的东西会缺；现在先排后截，砍掉的是**相关性最低的那些**；
- **对象列表页不再把相关性抹掉**：那一页以前无论怎样都按 id 或标题重排一遍，
  等于把服务端刚算好的次序推翻。现在排序档位多了一个 `relevance`（有检索词时的默认档），
  用户显式选了别的档才以他的选择为准；
- **每条结果写出命中理由**：标题命中 / 旧名命中 / id 命中 / **仅摘要命中**（橙色）。
  最后那一类必须说出来——它就是「看起来不相关却排在列表里」的那一类，不给理由等于让用户猜。

验收：`tests/search-rank.test.mjs`（11 项：五条判据各一条、两处实现逐字一致、
用户报的那一例、集合不变）、`tests/api.test.mjs` 的接口次序断言、
`tests/search-order.mjs`（真浏览器 10 项：面板里搜「紧」的次序与理由、清空后回到浏览次序、英文站）。

### 从节点页回到网络视图（2026-10 加）

**用户的要求**：「在网络中打开具体节点之后增加返回网络视图的选项。」

**要解决的具体麻烦**：网络视图的状态几乎全在 URL 上（`?nodes=` 是已加入的节点，
`play/entry/path/goal/route` 是结构回放）。从网络点进节点页之后那条查询串就丢了——
走完一圈回来，面对的是**另一张图**。

**做法**（实现在 [`web/src/network-return.ts`](web/src/network-return.ts)）：

| 存什么 | 存在哪 | 为什么 |
|---|---|---|
| 那一张图的 URL 快照 | `sessionStorage`，**按节点 id 分开** | 它是**一次浏览会话的上下文**，关掉标签页就该结束；写进 URL 会让节点链接长得无法分享，写进 E 会污染学习事件 |
| 「从哪来」这一个事实 | URL 上的 `?from=network` | 它必须能分享、能在刷新后保留 |

**界面分两档，如实区分**（节点页 `.node-return`）：

| 情形 | 给什么 | 依据 |
|---|---|---|
| URL 上有 `?from=network` **且**会话里有快照 | 「← 回到网络视图」，回**同一张图**（`nodes` 与回放参数都在） | 「回到你刚才那张图」 |
| 直接打开节点地址（分享链接 / 书签 / 换设备） | 「在网络视图里打开这个节点」（`/network?nodes=<id>`），并写明**为什么**没有「刚才那张图」 | **不编一个假地址**——这正是「如实登记」而不是「装作知道」 |

四条细节：

- **网络里 6 个节点链接全部走同一个 `nodeHref()`**（回放条、推荐面板、详情面板与三处关联列表）
  ——逐个手写 `encodeURIComponent` 一定会漏一个，漏掉的那个就是「从这里点进去回不来」；
- **快照只收与图有关的参数**（`nodes` 与回放五件套）：`from` / `locale` / 其他筛选一律不进；
- **语种跟着当前页面走**：中文存的图在英文站上返回 `/en/network?…`，不会把英文读者送回中文页
  （判据只认 `/en` 前缀，不用字符串包含）；
- **最多留 10 条**（先进先出）：这是浏览上下文，不是档案。

验收：`tests/network-return.test.mjs`（9 项，纯函数与边界）与 `tests/network-return-page.mjs`
（真浏览器 17 项：两档入口、真点回去落在同一张图、回放与英文站、390px 无溢出）。

### 切页回来自动恢复同一张图（2026-10-13 加）

**用户的要求**：「一次学习中搭建的网络视图要暂时的保存下来，不能有切到另外一个页面之后就需要重新搭建的情况。」

**麻烦在哪**：这一页的状态几乎全在 URL 上（`?nodes=` 是已加入的节点，回放五件套是结构回放），
而**侧栏导航、浏览器历史、书签、直接输入地址都不带查询串**——「搭好一张图 → 去别的页看一眼 →
点回知识网络」面对的是空画布。节点坐标、面板位置、排法早有本机存储，唯独「这一张图是什么」会丢。

**暂存什么、存在哪**（实现在 [`web/src/network-draft.ts`](web/src/network-draft.ts)）：

| 存什么 | 存在哪 | 为什么 |
|---|---|---|
| 已加入的节点 id、可见边源（七类边开了哪几类）、相机（平移 + 缩放） | `sessionStorage` 的 `mcs-network-draft-v1` | 它是**一次浏览会话的上下文**：关掉标签页就结束。写进 URL 会让地址栏跟着每次拖动变；写进 E（学习者档案）会污染学习事件；写进 `localStorage` 会让「上一次学习」跨天冒出来 |

**权威顺序**（谁说了算）：

| 情形 | 用什么 | 依据 |
|---|---|---|
| URL 上有 `nodes`（分享链接、学科导读的「在完整网络中探索」、书签） | **URL 为准**，不看暂存 | 别人给的图不该被我自己上次的图顶掉 |
| URL 上没有 `nodes`，且不在结构回放里 | 用暂存恢复（节点集合 + 边源 + 相机），并**立刻写回 URL** | 于是刷新与「复制当前链接」照样得到同一张图 |
| 正在结构回放（`play=1&…`） | 不读也不写暂存 | 回放期间 `added` 是路线在驱动的，插一手会两边都坏 |

五条边界，都是踩过之后定下来的：

- **恢复只改本页显示**：不改公共本体（M）、不写学习者档案（E）、**不产生学习事件**——与「保存的视图」同一条边界；
- **「清空画布」只作用这一次**：空集合永不覆盖暂存，因此清空之后切页回来拿到的是**最后一张非空网络**
  （清空旁边那个撤销入口管的是这一次）。想真的从新开始，用恢复提示条上的
  **「丢弃暂存，重新开始」**（带确认），它才连暂存一起删；
- **两个「清空」动作都要挡住自动恢复这一页的后续**：清空会让 URL 上的 `nodes` 消失，而恢复那一支
  认的正是「URL 没有 nodes」——不在用户明确清空/丢弃之后关上恢复，清空的那一帧就被恢复填回来
  （实测：点「清空」之后节点立刻回来，等于按钮没反应）；
- **相机是「钉住」之后放回来的**：落相机之后几百毫秒里 HUD 高度与画布尺寸才刚量出来，
  而「加入节点后自动适配」把量的结果也算进签名——不钉住就会被那次适配换成 `fitView` 的值
  （实测：离开时 `scale 3`、回来变 `2.9777`）。钉住 600ms，**用户一动手（指针按下 / 滚轮）立即松手**；
- **载入一张命名的视图时顺手清掉暂存**：显式动作胜过隐式恢复。

**不做**：不进「保存的视图」列表（那是用户手动命名的长期快照，可写 E、可导出）；不做跨天跨浏览器的自动恢复
（那要先回答「什么时候算一次学习」）；加载入/并集合并（与视图快照同一条边界）。

验收：`tests/network-draft.test.mjs`（13 项：该存的存、该退的退、坏数据不删原记录、边源键与渲染表一致）
与 `tests/network-draft-page.mjs`（真浏览器 32 项：切页回来是同一张图、刷新与浏览器后退、
显式链接优先、相机与边源一起回来、清空只作用这一次、丢弃之后不再长回来、空画布不写暂存、
回放不污染、英文站与窄屏）。

### 动态交互（拖动节点 / 新边生成动画）

**拖动单个节点**：像 Obsidian 那样把卡片拖到任意位置。手动摆放在网格布局**之上**叠加（`applyOverrides`）——网格是算出来的，没有这层覆盖，节点会被下一次重算拉回格子。拖动只改坐标：不改边、不改度数、不改连通性，**不写公共本体（M），也不写学习者档案（E）**。位置按节点 id 存 localStorage，刷新后仍在原处；**双击节点**放回算法位置（边框为虚线即表示已手动摆放）。

三个必须处理对的细节：

- **区分点击与拖动**：位移 < 4px 算点击（打开详情），否则算拖动并吞掉随后的 `click`——否则想点开节点会因为它没动而失效。
- **位移除以缩放**：指针位移是屏幕像素，节点坐标是世界单位；不折算的话放大后拖一点点就飞出去。
- **拖动中做斥力，而不是放手时跳位**（2026-10-15 改，见下）。

#### 拖动时的斥力：被压住的卡片让开，而不是被拖动的那张跳走

用户的原话是「拖动节点使其与另一个节点靠近的时候会有闪的情况，是因为之前写的避免节点遮挡的逻辑，
现在改进为节点被拖动的时候会因为斥力相互挤压而不至于出现闪的情况」。旧实现正是「放手时跳位」：

| | 旧（放手时避让） | 新（拖动中斥力） |
| --- | --- | --- |
| 谁让开 | **被拖动的那一张**（螺线搜索找最近的空位） | **被它压住的那几张**（被拖动者留在指针下） |
| 什么时候 | 只在松手那一刻 | 每一帧 pointermove |
| 实测 | 拖到邻座中心松手：当场下移 **128px**、再飘 31px | 松手前后**零位移**（同一坐标），邻座被推开 **70px** |
| 有序摆位 | 布局跟着 `overrides` 每帧重算，23 步里 **5 步**有别的卡片在动 | 布局**冻结**，只有被碰到的那几张动（8 节点场景实测 1 张） |

实现分三块，各自都有明确的理由：

1. **纯函数** `repelFromDrag(placed, draggedId, position, options)`（`web/src/network.ts`）：
   被拖动者**一步不动**，被它压住的沿「相对重叠更小的轴」让开，位移 = 压入深度 + 0.5 余量。
   因为位移与压入深度成正比，指针走 1px 邻座也只让 1px——这就是「不闪」的机械保证
   （`tests/network-repel.test.mjs` 直接量这条比例关系）。每一轮**以「拖动者 vs 其余」收尾**：
   「被挤开的互相压」那一步会把卡片推回去，正好推回拖动者身上，少了这个收尾，
   放手时的兜底会以为还有冲突、又把被拖动的那张挪开 70px。
   **收敛靠「间距逐档放大」**：固定间距下三张以上互挤会原地打转（A 推 B、B 推 C、C 又压回 A），
   实测真浏览器里留下过一对残余重叠——这与 `relaxToSpacing` 是同一个坑、同一条经验；
   只在「按基础间距仍然冲突」时才放大，因此普通情况让开量不会变大。
   拖动中只看被拖动者附近一圈（`minDx×2 / minDy×3`），放手那一次用 `full: true` 处理全部——
   每帧的预算与一次性的正确性本来就该用两套口径。
2. **拖动层**（`NetworkPage.tsx`）：`dragPosition` / `dragPushed` 是**瞬态**，不写进 `overrides`。
   写进去的话布局的依赖每帧都变，有序摆位会跟着重算（那正是「闪」的来源）。
   布局算完之后把这一层**叠上去**（`applyOverrides(fitted, {...pushed, [dragId]: dragPosition})`），
   因此拖动期间布局本身是冻结的——`__mcsNetwork.columns` 在拖动前后逐字相同，验收直接钉这一点。
3. **落点记账**三条规则：有序摆位 → 手动位置（那两档位置由规则决定，规则里没有「被顶开一点」
   这种状态，不钉住就会被拉回原层/圈）；**本来就是手动摆过的 → 更新它的手动坐标**
   （写进自动缓存会被 `overrides` 盖掉，卡片实际没动、重叠留在原地——实测踩到过一对残余重叠）；
   其余 → 自动摆位缓存（「系统让位」不是「用户摆的位置」：实线、不标手动，可被「重新布局」再算）。

顺带修掉的两个相机问题（都由这一轮的验收暴露出来）：

- **适配要按点模式算包围盒**：低倍率下节点是圆点 + 名字，屏幕尺寸是**常量**，
  而卡片是「世界尺寸 × scale」。按卡片估包围盒，缩到 25%（下限）时底边会短 15px、左右会窄——
  名字正好压进底部控制台。现在把「屏幕常量 − 卡片屏幕尺寸」的差额折算成世界单位补进包围盒，
  再适配一次（两轮收敛）。
- **回放只框这条路线**，并加了「放不下时贴可用区底边」的兜底：回放期间只有路线上的节点可见，
  让看不见的节点决定镜头等于「看不见的东西决定视野」；而当内容在最小缩放下仍比可用区高时，
  居中会让它往下压进控制台，现在改成溢出的部分全部往上走（顶栏是薄薄一条常驻导航）。

`avoidOverlaps`（旧的螺线搜索）**保留为兜底**：斥力解开之后它通常返回 `null`（即原地保留、不跳位），
只在「指针最后一下跳得太远」或「邻座被夹在一堆卡片中间推不动」时才真的移动。

验收：`tests/network-repel.test.mjs`（算法层 8 项：拖动者不动、让开量刚好、位移与压入成正比、连锁、确定性、越界不抛错）、
`tests/network-placement.mjs`（真浏览器：松手不跳位、邻座连续让开、全程无重叠、有序摆位下布局冻结且没有整卡跳位）、
`tests/browser.mjs`（「拖到别的节点上不会留下重叠」+「被拖动的那一张停在落点」）。

**加入新节点后相机平滑居中**：节点数增加时，视角**平滑地**（rAF 补间 460ms、ease-out cubic）移到以新节点为中心，
缩放不变；其余结构变化（删节点、切边源、回放）仍是 `fitView` 适配整张图。用户一动（滚轮、拖空白）就取消动画——
「相机自己在动、手却拖不动」是最难受的手感；`prefers-reduced-motion` 下直接跳，不补间。
不用 CSS transition 的原因：相机是 React 状态，拖动与滚轮会直接写它，过渡进行中用户一拖，落点会由插值决定而不是指针。
实现见 `centerOnNode` / `animateCamera`，验收见 `tests/network-camera.mjs`（8 项，含「途中采样落在起点与终点之间」）。

**新加入节点的自动摆位**：加节点时不再重跑全局力导向（那会把整张网络重排一遍，也不保证与手动摆放的节点不重叠），
而是**增量摆位**（`web/src/node-placement.ts`）：已有节点一个都不动，只给新节点在**邻居质心**周围
的极坐标网格上挑位置（7 个半径 × 24 个方位，含质心本身；方位相位由节点 id 派生，**确定性、不用随机数**）。

- **硬约束**：与任何已摆卡片不得重叠（水平 ≥ 172+24px、垂直 ≥ 58+16px），且不越出左上留白；
- **软目标**：`交叉数 × 4000 + 新边总长 × 1 + 离质心位移 × 0.6`——交叉权重远大于边长，
  宁可连边略长也不与已有关系缠在一起；
- **度数高的新节点先放**，邻居随后贴着它摆；
- 极端情况下退化为螺线搜索、再不行放到已有卡片右侧，**任何情况都不重叠**；
- 交叉只数**真交叉**：共线重叠算，端点相碰（共享端点、T 形相接）不算。

摆位结果缓存在 `mcs-network-placements-v1`（与手动位置 `mcs-network-positions-v1` 分开），
移出视图的条目顺手清掉。优先级：手动位置 > 上次的自动摆位 > 本次新算。
验收见 `tests/node-placement.test.mjs`（算法层 8 项）与 `tests/network-placement.mjs`（真实页面 13 项；
其中拖动那一段**不固定拖 DOM 序里的第一个节点**，而是用 `elementFromPoint` 挑一个真的点得到的——
HUD 与悬浮框都压在画布上，固定取第一个会变成「恰好没被盖住」这种版面巧合）。

**有序摆位（学习顺序 / 逻辑核心）在这一层之外**：那两档不读也不写 `mcs-network-placements-v1`
（位置由规则每次重算），但手动位置照样优先，规则卡片绕开它们。见「重排模式」一节。

**新加入节点的生成动画**：指向新节点的边用 `stroke-dasharray` + `stroke-dashoffset` 从「未画出」画到完整（620ms），新节点淡入并轻微放大（520ms）。路径长度由渲染处作为 `--edge-len` 传入，因此长短边的动画速度一致。**方向也一致**（2026-10-15 加）：新边一律从**已经在场的那个节点**长向新节点——`<path>` 的起点固定在结构方向 `edge.from`，而结构方向与「谁先出现」是两件事，因此起点是新节点时反过来揭示（`--edge-len-neg`，`network-edge-draw-from-end`），读起来才是「已有的知识接上了它」，而不是新节点伸手去够。放缩关系的实心带子是唯一例外（填充形状画不出虚线，只能用透明度，终点取它自己的档位不透明度 `--edge-opacity`）。

一处容易踩的坑：**入场缩放必须挂在内层 `<g>`**。CSS 的 `transform` 会覆盖 SVG 的 `transform` 属性，直接给带 `translate` 的那层加 `scale`，节点会掉到画布原点。位移（属性）与缩放（CSS）分层才能叠加。

`prefers-reduced-motion: reduce` 时全部关闭。

### 形状切换：只有很大的视图才用方块（2026-10-16 改）

用户原话：「只有视图很大的时候节点形状用方块，其余视图用圆点。」——阈值从「55% 以下圆点 / 65% 以上卡片」
改成 **「100% 以下圆点 / 120% 以上卡片」**（`web/src/network-workspace.ts` 的 `DOT_THRESHOLD` / `CARD_THRESHOLD`，
中间是滞后带：捏合时在带内保持上一次的形状，不会一格一格地翻）。依据是**卡片上的字能不能读**
（卡片里的文字跟着相机一起缩放）：

| 比例 | 标题（12.5 单位） | 节点 id（mono，约 9.5 单位） | 读得出来吗 |
| --- | --- | --- | --- |
| 65%（旧阈值） | 8.1px | 6.2px | 读不出来——旧阈值一直在画「看不见字的卡片」 |
| 100%（新圆点上限） | 12.5px | 9.5px | 标题勉强、id 吃力 |
| 120%（新卡片下限） | 15px | 11.4px | 两行都舒服 |

首帧形状取**圆点**（`useState<'card' \| 'dot'>('dot')`）：滞后带里 `nextNodeShape` 保持「上一次」的形状，
而首帧没有上一次；初值若是卡片，105% 这种落在带内的比例冷启动时会显示卡片，规则当场失效。

**名称上限随比例放宽**（`dotLabelMaxChars(scale)`）：7 个字那条上限是为 25% 档（圆点间距中位 27px）定的，
而圆点档现在是绝大多数视图的常态。放大时圆点在屏幕上被拉开（100% 下最近邻中位约 190px），
仍旧截到 7 个字就是白丢信息。因此 60% 以上给 10 个字、90% 以上给 14 个字
（卡片自己也是 15 个字截断，两档给的量级一致，切形状时不会突然多出/少掉半句话）。
实测 18 节点视图：47%（自动适配）14 个标签、最长 7 字 → 82% 18 个标签、最长 11 字 → 94% 最长 13 字 → 124% 翻成卡片。

### 圆点档的名称标签：写在圆点正下方（2026-10-15 加）

### 首页「继续学习」= 局部网络视图

首页的「继续学习」不是一句提示，而是一张**以你上次学习的节点为中心**的局部网络图：

- 中心 = 最近一条 `view` 事件对应的节点（没有阅读记录时退回「复习队列首项」或「第一个可学节点」，并如实标注是哪种来源）。
- **上 / 右 / 下 / 左 各对应一个话题**。中心所属话题固定放「上」，其余话题按「与本中心的强关联条数」降序排进 右 → 下 → 左。**没有邻居的方向不画**——不为凑满四格而编造话题。
- 同一方向内，**离中心越近关联越硬**。

「强关联」只取本体里已登记的依据，按强弱排序，同一节点只保留最强的理由：

| 依据 | 来源 | 强弱 |
|---|---|---|
| 登记关系 | `relations` | 最硬（带种类与见证状态） |
| 行动契约 | `actions` 的输入/输出 | 次之（中心是产出看前提、是前提看产出） |
| 共用前提 | 同一行动的两个输入 | 更弱 |
| 同一话题 | `aggregates`（只取 `topic` 类型） | 最弱（仅登记上的同组） |

没有这四类依据的节点不进这张图——它是「有据可依的下一步」，不是「全体近邻」。已确认掌握的节点不再重复推荐。`discipline` 类型的聚合被刻意排除：粒度过粗（「分析」会把极限与微分几何混在一起），不适合当方位话题。

实现是纯函数 [`web/src/continue-network.ts`](web/src/continue-network.ts)，不读时间、不读随机数。排版**按卡片几何求解**而不是试参数：两张卡片重叠当且仅当 `|Δx| < 卡宽` **且** `|Δy| < 卡高`，所以径向步长取「卡高 + 16」、切向取「卡宽 + 20」即可保证不重叠；画布尺寸由实际落点包围盒决定（按话题数估算会裁掉最外侧卡片）。

### 首页「原型问题」：按领域归类

栏目从「目录」改为**从问题进入**：每条思路先给「胚子」（最初那个具体困惑），再给形式结构、边界与落点。按**领域**分组，领域取自每个节点自己的 `discipline` 字段，而不是给案例硬贴标签——案例是「一条思路」，领域是「它在数学里的位置」，两者是多对多的：

| 分组 | 案例（括号内为该案例节点数） |
|---|---|
| 分析 | 极限与连续（16） |
| 微分几何 | 微分几何（38）、$C^k$ 与光滑流形（17） |
| 群论 | 群的多来源（15） |
| 多重线性与张量代数 | 张量与张量场（17） |

`sectionOf()` 的分组名单与 `data/fields.mjs` 的 FIELDS **一一对应**，2026-10 跟着学科细分同步更新过：
第五十二轮把教材式的合并标签（几何与拓扑 / 代数与几何 / 方法论）拆掉之后，旧名单一个都不再匹配，
分组界面退化成「分析 + 其他」两组——这是 `tests/browser.mjs` 的「按领域分组」断言抓出来的。

归组用**多数学科**：微分几何的 38 个节点里 28 个「微分几何」、5 个「拓扑」、3 个「分析」、2 个「多重线性与张量代数」，取任意一个会随机落到几个分组里。同时卡片上列出**完整的学科分布条**，不把「它也横跨分析」藏起来。

卡片上的量化信息**全部由本体现场派生**（[`web/src/case-catalog.ts`](web/src/case-catalog.ts)），不写死：节点数、学科分布、构造分布（概念/命题/证明/例子/反例/构造/问题/方法/误区各几个）、行动契约数与关系数、证据等级分布，以及直接可点的**反例与误区**链接——这是「条件即反例」「预见常见误解」两条要求在界面上的落点。

测试里有一条断言专门核对**卡片节点数与 `/ontology/graph` 的真值一致**，防止数字写死后与 `data/` 脱节。

一处渲染细节：`C^k` 在卡片标题里要经 Markdown 排版（否则被 GFM 当成上标语法，渲染成带脱字符的 `C^K`），而 `<option>` 与 SVG 文本不能排版，走 `plainMathText()` 换成 Unicode 上标（`Cᵏ`）。

### 方法节点与「局部技巧自动加入」

本体里有 **16 个方法节点**，按既有分类分成两类（`data/authoring.mjs` 的 `method()`）：

- **局部技巧**（`LocalMethod`，13 个）：任务形状明确、步骤可枚举，换一个场景不一定适用。例：用反函数定理核验候选映射、用小阶乘法表核验公理与交换性。
- **全局方法**（`GlobalMethod`，3 个）：跨场景策略。例：寻找不变量、从特例抽象共同运算。

五个案例各有 2–4 个方法。方法不是命题——**可以核对步骤，不能被证明**。因此每个方法的证据等级只写 `DEF` 或 `ILLUSTRATION`（绝不写 `PROOF`），并写明「未编码为 ND 证书」这一义务；测试里有断言守住这条。

dg 案例的方法正文写在 [`data/cases/06-dg-methods.md`](data/cases/06-dg-methods.md)，**不与生成的 `05-differential-geometry.md` 混放**——后者每次重跑生成器都会覆盖。

**推荐加入面板按分类分组**（局部技巧 / 全局方法 / 概念与定义 / 断言与证明 / 例子与反例 / 问题与练习 / 表征 / 其它），顶部有分类筛选 chip。画布上方法节点带左侧色带（局部技巧青色、全局方法紫色）。

**「补齐方法节点」是一次显式操作，不是副作用**：局部技巧与视图建立**超过三条**链接时会被列为候选，提示条说明有几个、都是谁，点「加入这 N 个」才真的进视图。判据是「它的直接邻域 ∩（视图 ∪ 视图的一跳邻域）> 3」——不是「与全库相连数 > 3」（那等于无条件加入，实测一个背景节点就能拉进 11 个方法），也不是「只数视图内直接连接」（方法节点连的是引入它的行动契约而非概念，那样任何方法都触发不了）。被手动移除过、或点过「暂不」的候选不会被再次加回。

**右键节点 = 节点菜单（2026-10 加：一键加入全部硬前置）**。原先右键只有「点一下把节点移出视图」
一个含义；用户要的是「从节点出发做事」，一个含义的位置放不下第二件事，于是右键改成打开一张小菜单：

| 菜单项 | 做什么 | 依据 |
|---|---|---|
| **加入全部硬前置（还差 N 个）** | 一次把这个节点的**全部硬前置**放进视图——直接的和间接的都算 | [`web/src/hard-prereq-closure.ts`](web/src/hard-prereq-closure.ts)：沿 `hardPrereq` 的 `to → from` 做广度优先；按钮上的 N 是「还差几个没进视图」 |
| **从视图移出** | 旧行为换了入口（`Delete` / `Backspace` 仍然直接移出） | 只改本页显示，不删本体节点 |

闭包的三条约定（[`tests/hard-prereq-closure.test.mjs`](tests/hard-prereq-closure.test.mjs) 逐条钉住）：
**只沿 `to → from` 走**（反向的一般化/应用/跨域接口不是「学它之前要先会什么」）；
**确定性**（同层按登记顺序，两次调用逐字相同，视图不会因为重算而抖）；
**成环不死、撞上限如实说**（`truncated` 为 true 时菜单写明「只加入前 N 个」）。
菜单里同时说明「含间接前置」与「只改本页显示，不写本体、不写学习记录」——它不改 M，也不写 E。

交互细节：都已在视图里时该项**禁用并写明**（不是点了没反应）；没有登记硬前置的节点显示
「这个节点没有登记硬前置」；`Esc` 与点空白都能关；键盘 `Shift+F10`（系统约定的上下文菜单键）
打开同一个菜单，焦点落在第一项，回车即执行。**触摸设备没有右键**，因此同一个动作在
「节点详情」面板里也有一颗按钮「加入全部硬前置（还差 N 个）」——两处调用的是同一个
`addHardPrereqs`，判据只有一份；差别只在「还差 0 个」时：菜单里禁用并写明，详情面板里直接不显示
（菜单是「这个节点能做什么」的完整清单，少一项会让人以为功能没了；详情面板是任务入口，没事做就不占位置）。
一次加进来一批时相机走 `fitView` 而不是居中某一个新节点——那批节点是「这个目标需要先会的一整片」，
居中排序最后的那个会把其余几个甩到视野外。验收见 [`tests/network-node-menu.mjs`](tests/network-node-menu.mjs)
（19 项，期望值由测试自己从 `/api/v2/ontology/graph` 重算一遍，不 import 被测实现）。

**左键按住节点（≥250ms）= 强关联节点选择器**（添加节点的新操作逻辑，2026-10 加入；手势最初在右键，同月改为左键）：
强调这个节点、把其它节点与所有边虚化、悬浮面板淡出让路，然后围着它摊开一圈
**还没进视图的强关联节点**——候选来自 `web/src/node-related.ts`：已登记关系（强度 = 关系权重 × 见证修正）、
该节点作为输入能引入的节点（契约 mode 权重）、引入它自己需要的前提，以及兜底的「共用前提」。
保持按住、把鼠标移到某个候选上（虚线强调环），**松手就把它加入视图**并落在它被摊开的位置，URL 同步。
松在别处或按 `Esc` 取消。

左键现在有**三个含义**，靠**位移**分流而不是只看时间：按住不动 ≥250ms → 选择器；
位移超过 4px → 拖动（长按计时立刻作废，拖到一半不会弹出选择器）；不到阈值就松手 → 点击打开详情。
选择器打开时会**主动释放指针捕获**，且 `onNodePointerMove` 在选择器存在时直接返回、不拦截事件——
否则挂在 window 上的悬停判定收不到事件，候选高亮会失效（左键按下有指针捕获，右键那版没有，所以从前没暴露）。
验收见 `tests/network-picker.mjs`（按手势每一步断言）。

### 布局是力导向：斥力 + 按关系强弱的吸力 + 话题配色

节点位置由**力导向**决定，不再走网格排布：

- **斥力**：所有节点两两相斥，并按**度数**加权——枢纽节点斥得更远，否则它会把一圈邻居压在身边、局部密到读不出来。
- **吸力按逻辑强弱分配**：直接取自 [`relation-visual.ts`](web/src/relation-visual.ts) 的视觉权重。硬关系（`hardPrereq` / `scaling` / 带 PROOF 见证）吸得最紧，行动契约次之，话题与共用前提几乎不吸（留 0.08 的底，避免同话题节点随机漂开）。**线宽、颜色、推荐理由的强弱顺序和这里的吸引强度出自同一个数**，不会出现「画得很粗却几乎不吸」这类自相矛盾。
- **尺度归一化**：力导向的绝对尺度与节点数无关，实测两个节点会被拉到 914×427（四面空白）、112 个节点又摊到 5147×6281。按节点数算一个目标面积整体缩放后，两个节点是 336×157、112 个节点是 3082×2853。
- **间距由 `relaxToSpacing` 处理**：力导向决定相对位置，后续松弛负责让卡片留出间距。历史实测 1 / 2 / 10 / 112 节点四种规模重叠均为 0；这是有限场景检查，不是任意输入无重叠的一般证明。
- **话题配色**：按本体的 `topic` 聚合**块**自动分组上色（不是整条聚合——dg 的 `agg-dg` 有五个块，整条当一个话题会让 30 个节点同色，等于没分组）。同一块同色，块序固定因此分配确定。未归入任何话题的节点用中性色，不硬塞进某个话题。图例只列**画布上真有的**话题与条数。

### 重排模式：学习顺序 / 逻辑核心（2026-10-11 加）

用户的要求（原话）：「在网络视图中，为重排节点位置的按钮添加模式切换功能，区分倾向于学习顺序的
节点位置和倾向于拟合节点天然的逻辑关系的节点位置：前者按照节点与起始节点的距离（隔了几个硬前置）
给节点分配上下的位置关系，起始节点在最上面，高阶的节点在下面；后者按照节点在视图中的节点群里面的
核心程度去决定节点在中心还是周围。起始节点和核心节点的选择交给用户，在网络视图页面里添加这个可选项。」

HUD 的「重新布局」旁边因此多了两个控件：**排法**下拉与**锚点**下拉。规则本体在
[`web/src/network-order.ts`](web/src/network-order.ts)（纯函数，node 侧可测）。

| 档 | 判据 | 位置怎么给 |
|---|---|---|
| **自由摆位**（默认） | 力导向：斥力 + 按关系强弱的吸力 | 相关的自然靠近；它不对「谁该在上、谁该在中间」表态 |
| **学习顺序** | 与起始节点隔了几个**硬前置**（只沿 `hardPrereq` 正向数） | 起始节点在最上面（第 0 层），层号越大越靠下；同层按「上一层的前置列重心」排左右（Sugiyama 的重心法），一层超过 10 列折行 |
| **逻辑核心** | 在**当前视图**这张图里的核心程度 = **加权 PageRank**，权重与线宽 / 吸力**同一个数** | 核心在圆心，其余由内到外分圈；圈内角度按内侧邻居的角度重心排，因此相关的落在相邻角扇区 |

- **锚点由用户选**：下拉只列**当前视图里**的节点（这两种排法说的都是「这一张图怎么摆」）。
  学习顺序的候选把「按你的档案现在就能开始」的排在最前（与卡片上那圈绿色描边同源），
  其余按登记前置由少到多；逻辑核心的候选按核心程度由高到低。第一项是「**自动：<它会挑谁>**」
  ——不选也能看见规则会挑哪一个，而不是一个空值。模式与锚点记在本机
  （`mcs-network-layout-mode-v1` / `mcs-network-layout-anchor-v1`），**不进 URL、不进保存的视图快照、不写 M / E**。
- **学习顺序有一条边界**：只沿硬前置**正向**数层，因此起始节点自己的前置、以及与本条顺序无关的节点
  **不在这条顺序上**——它们单独放在最下一层（`offBand`），界面在提示里如实说明，
  不假装它们是后续内容。
- **手动摆放仍然优先**：三种模式下手动拖过的节点都留在原处，规则摆出来的卡片绕开它们。
  分圈模式的让位沿**半径向外**走：用通用让位（先垂直再水平）实测会把一整圈卡片挤成一条竖线，
  圆心到其余节点质心的距离从 60px 涨到 457px，「核心在中心」直接读不出来。手动卡片与规则卡片
  重叠时**如实重叠**（那是使用者自己放的位置；锚点不会被推开，否则规则本身就毁了）。
- **可以不要这个优先**：「重新布局」左边有一个**「保留手动摆放」勾选**（默认勾上 = 老行为）。
  取消勾选再点「重新布局」，这一次重排会把你手动摆过的节点**也一起归位**，位置全部重算，
  并留一个「**恢复手动摆放**」的撤销入口（与「清空画布」的撤销同一种做法）。
  勾选状态**不落本机存储**：它是「这一次怎么排」的选择，不是长期偏好——存下来的话，
  隔一天回来点「重新布局」会把手动摆放悄悄清掉，那正是这个选项最该避免的意外。
- **两档规则都是构造上不压卡片**：列距 208px / 行距 104px / 圈距 210px / 同圈最小弦长 200px，
  都大于卡片对角线所需（√(172²+58²) ≈ 182）。也都是**纯函数**：同一输入逐位得到同一坐标。
- **切回自由摆位**：回到力导向那一套。有序模式**不读也不写**自动摆位缓存，因此切走前的那张摆位还在。

**同一轮顺带修的相机留白**：HUD 是压在画布上的浮层，原先无论多高都只让出 64px，
而实测 HUD 在 1500px 下 114px、1024px 下 159px——内容顶部一直压在 HUD 底下
（往 HUD 里加这两个控件时当场压住了一张卡片，`tests/network-placement.mjs` 的拖动因此点在了 HUD 上）。
现在留白 = `max(64px, 量到的 HUD 高度 + 8px)`，常数降级成**下界**（首帧仍用它兜底）；
窄屏 HUD 在画布下面排着，留白照样是 0。

2. **滚到下一幕**：进度到端点之后，下一次滚轮才把页面平移到下一段（`PLAY_DISTANCE = 560` 约 6 格播完一幕，

反向同理：先倒放本幕动画，倒到头才回到上一段。报头吸顶并显示本幕播放进度条；

### 学习路线 → 节点网络回放

路线页每条路线卡上有一个 **「在网络里回放这条路线」** 按钮，把这条路线送到组建网络页，从几个起点节点出发、按规划的事件顺序逐步向外扩张。URL 形如 `/network?play=1&entry=…&path=…&goal=…`；**把展开顺序直接写进 URL** 而不是只传路线 id——规划器结果不入库，路线 id 换个档案或预算就失效，写进 URL 之后刷新与分享都能复现同一段动画。

回放是一个**可调状态的动态系统**，不是一段只能看完的视频：底部控制台有起点 / 上一步 / 播放·暂停 / 下一步 / 终点 / 倍速 0.5–4×，以及**可任意跳步的进度条**；每一步都显示「这一步加入：<节点>」与「用到的已有节点」。

实现上两件事值得记住：布局**只算一次**（进入回放把已加入集合设成整条路线，可见性在渲染期过滤，因此步骤切换时位置不跳）；回放**不写任何状态**——进度、播放、倍速都是页面局部状态，不写 URL、不写本体、不写学习档案。

代码在 [`web/src/route-replay.ts`](web/src/route-replay.ts)（纯函数，可单测）与 [`web/src/pages/NetworkPage.tsx`](web/src/pages/NetworkPage.tsx) 的回放控制台。

#### 多程合一图：把一本教材的好几程放进同一张视图（2026-10-15 加）

范例路径把一本教材切成若干「程」，每一程单独载入、单独规划、单独回放。但常被问到的下一件事是
**连着的好几程**：第一阶段立起来的语言，在第二阶段是怎么被接着用的——程与程之间的接口正好落在两张图的边界上。
因此展开一本教材后，每张程卡片上多了一个「选这一程」勾选框，选好再点
**「放进一张网络视图（N 程）」**，这几程就接成**同一条回放**。

合成规则是纯函数 [`web/src/example-combined.ts`](web/src/example-combined.ts)：

- **起点**取所选里**最早那一程**的起点——`buildPaths()` 已保证「第 n 程的起点 = 基础背景 + 前 n−1 程的全部里程碑」，
  所以未勾选的程的里程碑也已经在场（那是「走到这里时它们已经在手里」）；
- **展开序列**按程的先后把各程 `goals` 依次接上、**去重**（后面的程会重复登记前面已经拿下的节点）；
- **程边界**逐程记下「贡献了几个新节点、从第几步开始」，这是这个功能的意义所在；
- 勾选顺序不影响结果（程的先后由数据决定）；越界与重复的下标直接丢掉；一程都没选时不渲染入口。

URL 只记**节点序列**与**程下标 + 步数**（`stages=2:5,3:4`），**不记程的标题**：
标题是本地化文本，写进链接会把中文带进英文站、也会让链接随文案变化而失效。
网络页按 `route`（教材 id）与下标回本地数据里查标题，查不到就只写「第 N 程」。
只勾一程时不写 `stages`——那时它就是普通的单程回放。

网络页据此做三件事：控制台标题下面写「第 2 程 · 数值序列与级数 · 7 步」；
面板底部列全这张视图里的各程（当前那一程高亮，0 步的程如实标「没有新节点」）；
**每一程的第一支箭头**在中点画一圈环（步号只说顺序，不说「换了一程」）。

那一圈环**不挂在步号徽标里**（2026-10-15 修）：徽标会被碰撞消隐（同一处挤着两支时只留一个），
挂进去的话「这一程从哪儿开始」会随步号一起消失——实测多程视图走到最后一步时少了一圈环。

一处必须一起改的地方：进入回放时 `setAdded` 会重写 URL（把节点集规范化），
它保留的键原本只有 `play/entry/path/goal/route`——漏掉 `stages` 的症状很隐蔽：
**回放照旧放得出来，程名与程的起点环静默消失**。现在回放参数一共六个键，
`NETWORK_PARAM_KEYS`（点进节点再回来的快照）与「退出手势回放」的清理列表都跟着同步。

验收：`tests/example-combined.test.mjs`（9 项：合成规则、去重、跳着选、程边界、URL 往返、宽松解析），
`tests/network-return.test.mjs` 钉住六件套进快照，`tests/browser.mjs` 走一遍真实动作
（勾两程 → 点按钮 → 网络页步数 = 链接里的节点数、控制台列全各程、两圈环、当前程写对）。

#### 路径箭头：细线、保留、按方向生长（2026-10-15 改版）

只让卡片逐张淡入，看的人能看出「又多了一个节点」，却看不出这一步是**朝哪儿去**的——帧与帧之间没有任何连线。
因此画布上画**路径箭头**：从**刚立住的那个节点**指向**下一步要立住的那个节点**，
末尾那一支是预告（目标还没出现，由一张带「下一步」徽标的卡片承担，源节点加一圈高亮）。

形状是**一条细线**（`web/src/stage-arrow.ts`）：主干 1.6px、箭镞 12px，都是**屏幕像素**
（几何按 `1 / scale` 换算成世界单位），因此缩放到任何比例都一样细、一样看得见。

上一版是五股渐细的丝带 + 凹边大箭镞。换掉它不是为了换风格，是量出来的：
丝带中段最宽 30 世界单位、箭镞长 26–62，在 54% 的回放比例下摊开成 100–225 × 98–273 屏幕像素的一大团，
盖住的正是它本该指出的结构。三条改动一起做：

- **细**。一条线说清「从这儿到那儿」，不必用一束光来说。
- **保留**。旧实现只画「当前这一步 → 下一步」那一支，走一步换一支，走过的全丢掉；
  回放完一遍只剩最后一支，看不出这条路线按什么顺序长出来。现在**每一步各留一支**，
  走过的暗一号、最新那支是主色并带一层极淡的外发光，顺序不读数字也看得出来。
- **编号**。每支箭头的曲线中点挂一枚小圆牌，写明这是第几步（屏幕上恒定大小）。
  排得太密时按「新的先占位」贪心让位——两枚步号叠在一起比少一枚更难读。
  悬停圆牌有 `<title>` 写着「第 k 步 → 节点名」。

两端的锚点按节点**当帧的可见外形**裁剪：卡片按矩形、圆点档（现在含 100% 以下的全部比例，见「形状切换」一节）按半径。
旧几何一律按卡片矩形算，圆点档下尾巴会停在离圆点四十多像素的空地上——看的人认不出它从哪个节点出发。
遇到力导向布局把两个节点放得比一张卡片还窄的情形（实测 12 步里有 3 步只有 68–85 世界单位），
直连的起点会跑到箭尖前面去；这时改走**绕行弧**：从侧向出去、侧向回来，弧线再往外鼓一个包，
于是每一步都有箭头，学习顺序不会缺号。两端完全重合（没有方向可言）时才不画。

生长动画分三段，读起来是「线先长过去，箭头才立住」：
主干按**自己的长度**从源头画出来（`stroke-dashoffset: var(--arrow-len) → 0`），
箭镞晚 460ms 落下（`stage-arrow-head-in`），同时一道短高光沿主干朝箭尖跑（`stage-arrow-flow`）。

#### 路径箭头绕开关系边、并且往外绕（2026-10-15 晚）

用户截图里的问题：**路径箭头和逻辑关系挤在同一条走廊里**——同一对卡片之间既有「硬前置」边、
又有这一步的箭头，两条线并排贴着，读起来混成一片。用户自己画了一张红线草图，
希望箭头像那样**从外面绕过去**。现在几何里加了三条规则：

- **关系边也是障碍**。可见的边（已按两端外形裁过，即屏幕上真的画出来的那一段）与卡片一起参与评分；
- **往外绕**。弧高候选按「由小到大、每档先外侧后内侧」排列，评分封顶（`ENOUGH_CLEARANCE_PX`，够空即满分）
  且用严格大于比较，于是同分时外侧那一条胜出；「外」由节点群质心（`awayFrom`）定义；
- **够得着**。卡片之间的可见走廊实测可以短到 **17–20 世界单位（约 27px）**，
  只按弦长的比例绕根本出不了那道缝，因此弧高候选里另有一族**绝对屏幕像素**档（20/36/60/92px）。
  圆点档下更常见：两个圆点中心距 40 世界单位时，扣掉半径只剩 11 世界单位——必然走绕行弧，
  而绕行弧的鼓包也改用同一族候选，于是它同样能甩到外面去。

判据是「中段并行重叠」：把箭头与每条边采样成折线，数箭头中段（25%–75%）有多少采样点落在某条边 3px 之内
（这正是「两条线并排跑」的量）。实测：

| 场景 | 直线走法 | 现在 |
| --- | --- | --- |
| 用户那条 4 节点路线（158%，卡片档） | 0.30 | **0.18** |
| 12 步路线（55%，圆点档） | 0.21 | **0.03** |
| 20 步路线（43%） | 0.39 | **0.03** |

20 步那一档「重叠过半」的箭头从 2 支降到 0 支；`tests/browser.mjs` 里还加了两条断言：
中段重叠率必须低于直线走法、且必须存在明显弓高（≥16px，即「往外扩散」真的生效了）。

代价与剪枝：关系边进入评分后，最重的 40 步路线（41 节点 / 66 条边）一次 **10.2ms**（12 步 2.0ms、20 步 3.3ms）。
两处剪枝把 23.5ms 降到这个量级——**够空就停**（候选按弧高排序，第一条达到封顶分的就是答案）
与 **赢不了就停**（每个候选的采样一旦掉到当前最优之下立刻返回）；外加按每支自己的采样盒再筛一遍障碍。

**关系边也跟着改**（同一天）：新加入的边一律**从已经在场的那个节点长向新节点**。
`<path>` 的起点固定在结构方向（`edge.from`），而结构方向与「谁先出现」是两件事：
一条以新节点为 `from` 的关系边照旧从起点揭示，就成了「新节点伸手去够旧的」。
因此起点是新节点时反向揭示（`network-edge-draw-from-end`，`dashoffset` 从 −L 走到 0）。
顺带清掉一处**同名 keyframes 互相覆盖**的旧缺陷：`.network-edge[data-new]` 那条固定 `dashoffset: 64`、
并把不透明度动画到 0.6 的 `@keyframes network-edge-draw` 写在后面，把按长度算的正经动画整个顶掉了
（同名 keyframes 后者胜），「把线画出来」于是退化成一次淡入。现在只剩一条按长度的。

几何是纯函数 [`web/src/stage-arrow.ts`](web/src/stage-arrow.ts)，不碰 DOM、不读测量值；
`tests/stage-arrow.test.mjs` 核对「细、贴、绕、留、编号不重叠、避关系边、同分往外」，
`tests/browser.mjs` 另外核对「箭头预告的那个位置，下一步真的在那里长出了节点」「走过的箭头被留住」
「最新那支真的在生长」「新边从已在场的节点长向新节点」以及「路径箭头不再与关系边并排挤在同一条走廊里」。

## 「数学对象」列表页（`/nodes`）

这一页的目标是「让学习者找到现在能读的那个对象」。三条硬约束写在代码里，也写在验收里
（`tests/node-list.mjs`）：

- **可达性**：接口默认只返回 200 条而本体已有 232 个节点。页面显式请求上限并前端分页
  （每页 60，「显示更多」），只有返回条数正好等于接口上限时才提示被截断。
  用 `total ≠ returned` 判断截断是错的——加筛选后两者本来就不等。
- **默认排序是「有正文优先」**（可切换登记顺序 / 按标题，依据写在选项旁）：
  登记顺序的开头是背景脚手架节点，全部「0 行动 0 证据」且无正文，让它们占满首屏是拿学习者
  的第一印象换资料完整性。排序是可见可切换的，不是偷偷隐藏节点。
- **诚实与状态**：无正文的卡片标「正文待写」；卡片读 E，标「已确认 / 已读 / 还不懂 / 现在可学」，
  并给「只看有正文的」「只看我没读过的」两个开关。列表**不写任何 E**。
- 卡面只显示有内容的数字（`N 条登记关系`、`N 种引入方式`、`N 条证据`），关系为 0 时写「暂无登记关系」，
  不再打印一串 0；标题与摘要走 `plainMathText`，纯文本上下文里不出现 `C^K` 这类脱字符。
- 窄屏把四个下拉收进「筛选」（默认收起）——改前 390×844 下第一张卡在 913px，整屏无内容。

## 筛选选项的规矩：只能从真有的数据里长出来

**下拉与筛选选项一律由 `web/src/facets.ts` 的 `buildFacet()` 从实际节点派生**，
不允许再用 `Object.keys(CONSTRUCT_LABELS)` 这类标签表直接铺选项。理由有一次真实报错：

- 标签表是「本体**模板**支持哪些类型」，节点数据是「现在**真有**哪几类」，两者混用就会产生死选项。
  本体 232 个节点里只有 11 类构造，而标签表有 14 类——「项 / 定义 / 表征」选中后永远是 0 个节点
  （`construct=Definition` 与 `role=Definition` 都没有登记过）。
- 因此 `buildFacet()` 返回 `present`（真有的类别 + 计数，供筛选）与 `absent`
  （模板声明、本体空着，**只用于如实说明**）。面板里会写明本体**没有把这几种内容登记成独立节点**，
  以及它们各自登记在哪里（见下面「构造类型的登记约定」）。
- **关系种类不是节点类型**：`analogy`（类比）在本体里只有 1 条关系、0 个节点。
  在节点列表或网络面板里搜到关系词时，`relationKindHint()` 会说明它是关系、给出本体里的条数与去处，
  而不是留一个空列表。
- 规矩由 `tests/facets.mjs` 钉住：无死选项、选项数 === 真实类别数、标注计数 === 实际筛出条数、
  空类别如实说明、关系词给出处。**新增筛选控件时按这条写。**

## 节点类别的划分（`web/src/node-groups.ts`）

推荐面板按类别分组，类别名必须与本体里真有的构造对得上——**不能凭模板想象**
（`tests/node-groups.test.mjs` 钉住这条）：

| 类别 | 收哪些构造 | 现在有多少个节点 |
|---|---|---|
| 概念 | Concept / Theory / Symbol / Construction（+ 模板里的 Definition / Term） | 137 |
| 断言与证明 | Claim / Proof | 51 |
| 例子与反例 | Example / Counterexample | 8 |
| 误区模式 | MisconceptionPattern | 11 |
| 问题与练习 | Problem | 4 |
| 局部技巧 / 全局方法 | Method（按 roles 分） | 21 |
| 表征 | Representation | 0（模板支持，未登记） |

两处刻意的措辞：这一组叫**「概念」而不是「概念与定义」**——本体里没有单独的「定义」类别，
定义写在概念节点的正文里（`construct=Definition` 与 `role=Definition` 都是 0）；
**误区模式单独成组**，不再并进「例子与反例」——常见误解在本站是一等对象。

## 构造类型的登记约定（Definition / Term / Representation）

本体的模板支持 14 种构造，但**这一点不等于它们都被登记成独立节点**。当前三种不是：

| 构造 | 在本站登记在哪里 | 依据 |
|---|---|---|
| `Definition`（定义） | 写在**概念节点的负载与正文**里：`formal.predicate` 就是定义式，节点正文给出「直觉 / 为什么需要 / 边界」 | 全库 `construct=Definition` 与 `role=Definition` 都是 0；定义性依赖由 96 条 `hardPrereq`（`definitional-dependency`）显式指出「依据在定义的哪一处」 |
| `Term`（项） | 写在**签名与类型环境**里：`signature.constants`（`d`、`·`、`e`、`⊗`、`∘`、`=`、`∀`、`∃`）与各节点的 `formal.typeEnv` | 形成检查只对已登记的项作类型检查（`core/typecheck.mjs`），不要求每个项都成为一个节点 |
| `Representation`（表征） | 写成**节点内的 `representations` 子记录**（31 条，分布在 29 个节点上）：`{id, kind, title, medium, status, note}`，节点页与 `/ontology` 的 `representations` 坐标都能读到 | 表征在本站是对象的表达方式，不是独立的学习单元 |

**为什么这样定**：把定义、项、表征都拆成节点会让节点数翻倍，而每一个都不可独立认知——
这与「节点是最小的可独立认知单元」直接冲突（第五十二轮的粒度分层就是为了这件事）。
所以本站的选择是：**这三类内容都登记了，但不作为独立节点**；界面因此不再说「本体里还没有登记」，
而是给出上面这张表里的去处。若将来要登记成节点，形成检查已就绪
（`core/formation.mjs` 里 `Definition` / `Term` / `Representation` 的字段要求都在，`data/authoring.mjs` 也有对应助手）。

`tests/construct-registry.test.mjs` 把这条约定钉住：三种构造的节点数为 0、文档里写明约定与去处、
界面文案不再声称「还没有登记」、以及筛选里不出现选中即 0 的选项。

- 节点、行动、证据、支持、关系与断言：data/cases/*.mjs 与 data/manifest.mjs，使用 data/authoring.mjs 的构造助手补齐形成字段。

### 重要节点的「形式表达」（`data/formal-statements.mjs`）

**16 个挑出来的重要节点**在 M 里多了一个字段 `formalStatement = { tex, reading, notation[], label, note }`，
节点页在正文之前用一张「形式表达」卡把它排出来：行间公式（KaTeX）+ 中文读法 + 记号表 + 证据标签 + 补充说明。

- **挑选依据**：按关联度（登记关系 + 行动契约参与）排序，补上四个案例的概念核心，只保留能写出无争议形式陈述的节点；**其余 216 个节点保持 `null`**，页面不留占位。
- **与 `formal`（形式负载）分开**：`formal` 是喂形成检查器的元数据（theory / type / symbols / boundary），`formalStatement` 是给人读的陈述。`tex` 不含 `$` 定界符（登记时校验，含 `$` 直接报错），渲染层补成独占一行的行间公式；`label` 必须是六种证据标签之一。
- **内容纪律**：陈述照本站已登记的措辞写。`dg:manifold` 是「Hausdorff + 局部欧氏」（不含第二可数），`dg:smooth-manifold` 才加第二可数——两份陈述的差别写进 `note`，并有测试钉住，不许「统一」成更常见的那一种。没有任何一条经过机器证明：`DEF` 表示按节点正文口径这是定义，`REF` 表示只是按教材陈述。
- **长公式在语义连接处断行**（`\\[4pt]`），不缩小字号：实测 1280 宽下 16 条全部完整可见。验收见 `tests/formal-statements.mjs`（19 项）。

### 已知的正文排版缺口

`formal.predicate` 与 `formal.formula` 目前共 29 个字段，**全部没有写 `$…$` 分隔符**。界面会安全地把其中 21 个纯公式字段包成行间公式排版；剩下 8 个含中文的字段（例如 `∀群 G ∃单同态 G→Perm(G)`）无法整体包裹而不破坏 KaTeX 解析，因此按普通文本显示。要让它们也排版，需要在这些数据字段里自行写出 `$…$` 边界——那是修改公共内容，属另一项决定。
（上面新增的 `formalStatement` 是**另一条路**：不动那 29 个形成检查字段，只在挑出来的节点上另立一份给人读的陈述。）

## 自动关系发现与验证（2026-10 首版）

**一条完整流程**：在网站填写新节点的**受限形式表达** → 系统**自动发现**候选关系 →
**验证**其中一部分 → 展示依据 → 审阅后把节点与选定关系加入公共知识网络。

入口两处：**节点详情页**的「以此为基础创建」/「检查已有形式表达」，以及**网站维护**的「自动关联」。
主流程固定六步：填写节点 → 检查表达 → 自动发现 → 审阅结果 → 入库预览 → 确认入库。

- **施工图**：[`docs/自动关系发现-接口与语言规格.md`](docs/自动关系发现-接口与语言规格.md)
  —— 语言语法、模块函数签名、数据形状、预算、服务层接口。代码与本文件不一致时，**先改文档再改代码**。
- **操作说明与覆盖报告**：[`docs/自动关系发现-操作说明与覆盖报告.md`](docs/自动关系发现-操作说明与覆盖报告.md)
  —— 怎么用、已覆盖 / 未覆盖 / 未验证三栏分开、本轮实测数字。
- **验收记录**：[`VALIDATION.md`](VALIDATION.md) 第五十九轮 —— 九条真缺陷的来龙去脉、未落实的边界。

**它独立于 AI 服务运行**：本机规则搜索、本机证明生成、本机独立检查。
自然语言/LaTeX 自动翻译、开放式类比发现、教学效果预测、完整数学证明助手**都不在范围内**。

### 三件必须先分清的事

1. **`formalSpec`（机器表达）与 `formalStatement`（给人读的陈述）是两份东西**，互不覆盖：
   后者是挑选出来的 16 个节点上的 LaTeX + 读法；前者是**可解析、可推理、可重算哈希**的登记，
   落在 `data/formal/registry.mjs`（34 条）。
2. **「检查器接受了这份证书」不等于「命题已获机器验证」**。`kernel.py` 自身
   `formally_verified: false`，结果里原样保留这个字段；`verified` 需要
   **kernel `passed` 且 §2.10 的目标核对通过**，两者缺一即 `undecided`。
   而「检查失败」**永远不等于**「命题为假」。
3. **有限语义只反驳它自己那个背景下的蕴含**。`core/formal/finite.mjs` 只检查预置有限对象
   （模 5 单位群、S₃），**不搜索任意模型**，也不把有限枚举的通过升级为无限结构上的普遍定理；
   找不到反例只返回未决。

### 两条读参数的约定（踩过的坑，写在这里免得再踩）

1. **服务端拿到的 `query` 是 `URLSearchParams`，必须用 `.get()`**。属性访问（`query.granularity`）
   永远得到 `undefined`——第五十二轮就是这样把 `granularity=topic` 悄悄降级成 `unit` 的，
   而且**不报错**（返回 200，只是内容不对）。服务端源码顶部与本节都写明这条。
2. **`scope` 与 `granularity` 不是一回事**，不要混用：
   - `granularity` 是**条目粒度**（`unit` / `topic`），属于节点；
   - `scope` 是**方法的适用范围**（局部方法 / 全局方法，`Method` 节点的 `formal.scope`）；
   - 关系的 `scope` 又是**这条依赖说的是什么**。
   三个同名概念在数据里是不同的字段；查询参数只有一个 `granularity`。

### `GET /ontology/nodes` 的查询参数

| 参数 | 取值 | 默认值 | 说明 |
|---|---|---|---|
| `granularity` | `unit` \| `topic` \| `all` | **`unit`** | 条目粒度。话题级条目是「一节或一章的范围」，默认不返回 |
| `q` | 任意文本 | 空 | 在 id / 标题 / 摘要里做小写包含匹配 |
| `discipline` | `data/fields.mjs` 的词表 | 空（全部） | 按本质领域筛（不是教材来源） |
| `construct` | 14 种构造之一 | 空（全部） | 按构造筛 |
| `role` | 13 种角色之一 | 空（全部） | 按角色筛 |
| `case` | 案例 id | 空（全部） | 按来源（案例）筛 |
| `limit` | 1–500 | 200 | 返回条数上限 |

响应固定带三个字段，便于调用方核对「我拿到的是哪一档」：

```jsonc
{
  "granularity": "unit",                 // 实际生效的档位（未知值回退成 unit 后如实回报）
  "granularityCounts": { "unit": 180, "topic": 52 },
  "total": 232, "returned": 180,
  "nodes": [ /* … */ ]
}
```

**迁移示例（第五十二轮的语义变更）**：`granularity` 是**新增**参数，不带参数时的语义
从「全部节点」变成了「只单元」。旧脚本若按旧行为数节点，会少看到 52 条话题级条目。

```js
// 旧调用（2026-10 之前）：不带参数 = 全部
const all = await (await fetch('/api/v2/ontology/nodes?limit=500')).json();
all.data.nodes.length;                     // 改动前 232，改动后只有 180

// 迁移：想连话题一起看，显式传 all（不要依赖默认值）
const everything = await (await fetch('/api/v2/ontology/nodes?limit=500&granularity=all')).json();
everything.data.nodes.length;              // 232
everything.data.granularityCounts;         // { unit: 180, topic: 52 }

// 只想看话题（学习线索）：显式传 topic
const threads = await (await fetch('/api/v2/ontology/nodes?limit=500&granularity=topic')).json();

// 未知值不静默改变语义：回退成 unit，并在 granularity 字段里如实回报
const unknown = await (await fetch('/api/v2/ontology/nodes?limit=500&granularity=nonsense')).json();
unknown.data.granularity;                  // 'unit'
```

话题级条目的判据与逐条判定结果在 `data/granularity.mjs`（话题清单 + 判为单元的例外，各带理由）；
校验器要求「标题命中并列词的条目必须有判定记录」，漏判一条 `npm run check` 就会红。

## DeepTutor 可选辅导

辅导入口复用 mcs-bridge 已核查的 DeepTutor 1.5.16 WebSocket 传输形状，但使用新版本体上下文与事件适配器，和旧协议、旧会话隔离。

**工作区里有两套 DeepTutor 集成，状态页会同时显示两边：**

| | 本站内适配器（`server/tutor.mjs`） | 桥接 `mcs-bridge`（3783） |
|---|---|---|
| 做法 | 把本体上下文注入指令，回答落 E 事件 | MCP 工具 + 事件登记 + 契约校验 + 轮次凭证 |
| 记录 | 事件写进本站 SQLite（E） | 写浏览器档案（E）+ 自己的账本 `runtime/state.json` |
| 权威性 | 本站自用 | **经过核查的那一套**（有 COMPATIBILITY 与真实联调记录） |

两者**不要混用同一档案的结论**。`/api/v2/tutor/status` 里的 `bridge` 字段是本机回环探测桥接公开 health 的结果。

### 两套集成的分工（2026-10 定稿，TODO A4-28）

第三十四轮的边界是：「站内适配器与桥接服务各自演化，只对齐了失败码与状态披露。
*验收*：给出合并方案（谁调谁、错误语言与事件登记归一），或明确「保持双轨」并写清分工与差异。」

**结论：保持双轨，不合并**。理由是两条路径解决的问题不同，合并会同时损失两边的长处：

| 问题 | 站内适配器 | 桥接服务 | 为什么不合并 |
|---|---|---|---|
| 谁调谁 | 页面 → 本站 `/api/v2/tutor/*` → DeepTutor WebSocket | 外部 Agent / DeepTutor → `mcs-bridge`（HTTP + MCP） | 一个是**本站的前端功能**，一个是**给外部工具用的服务**；调用方向相反 |
| 上下文 | 本站直接构造（`core/context.mjs`，按节点分档预算） | 走契约（`get_learning_context`，调用方给 `max_chars`） | 一个在进程内共享本体对象，一个必须跨进程传数据 |
| 记录 | 事件写本站 SQLite（E），带 `ontology_version` 与回合 id | 写浏览器档案（E）+ 自己的账本 `runtime/state.json`（含轮次凭证） | 账本形状不同：一个面向页面回放，一个面向外部调用的幂等与重放 |
| 工具面 | 无（只做讲解/提问/出题三类模式） | MCP 工具 12 个，可被外部 Agent 组合 | 站内不需要 MCP 这一层，外部需要 |

**已经归一的部分**（可以核对，不是「说好了」）：

1. **失败语言**：两边都用 `code` + `retryable` + `recoverable`。`recoverable` 的语义与码表在
   `shared/errors.mjs`（本站）与 `mcs-bridge/contracts.mjs`（桥接）各有一份，
   `tests/tutor.test.mjs` 会逐条核对同名码取值一致。已知的**码名分歧**只有一处：
   本站 `BAD_REQUEST` ↔ 桥接 `INVALID_ARGUMENT`（同一件事、两个名字，判定已经一致）；
   改名要动协议，留给单独一轮。
2. **上下文预算**：两边同口径三档（compact 8000 / standard 16000 / extended 24000），
   预算不足时报 `EVIDENCE_RESOURCE_EXHAUSTED`（本站）/ `CONTEXT_BUDGET_TOO_SMALL`（桥接），
   details 都带 `minimum_chars` / `tier` / `suggested_chars`。
3. **证据纪律**：两边都不把「配置齐全」说成「已验证」；`liveVerified` 由本进程内完成过的回合数决定。

**没有归一、也不打算归一的部分**：会话标识（本站 `tutor-<uuid>` vs 桥接 `session_token`）、
事件账本位置与格式、MCP 工具面。这些差异是**设计选择**，写在这里是为了让读者能判断
「我现在看到的状态是哪一套的」——状态页也据此把两边分开显示。

- DeepTutor 未启动时，/tutor/status 报告未连接；学习、图谱、路线与研究功能不受影响，页面不会伪造模型回复。
- 辅导反馈只追加 E 事件；模型评价不自动确认掌握，confirmed 必须由学习者显式确认。
- `liveVerified` 由**证据**决定：配置里允许（`MCS_WEB_TUTOR_LIVE_VERIFIED=1`，表示本机已完成核查）**且**本进程内真的跑完过回合。旧版只看配置开关——一个环境变量就能让界面声称「已完成真实验证」，还把该布尔值写进事件；现在事件里记的是 `completed_turns_in_process`（可追溯的完成次数）。
- 失败分类与桥接一致：回合中断报 `DEEPTUTOR_INTERRUPTED`（带 `turn_id`，页面不自动重发），握手阶段失败才是 `DEEPTUTOR_UNAVAILABLE` / `DEEPTUTOR_AUTH_REQUIRED`，三者都带脱敏 `details.cause`。
- DeepTutor 的全局画像与记忆不自动导入 E；多用户部署需要单独的账户隔离方案，本版本面向本机单用户、多档案。
- **版本号是运行期读到的**（2026-10 改）：服务端只读本机检出 `deeptutor/__version__.py`
  （见 `server/upstream.mjs`，缓存 5 分钟），把版本、来源路径与读取时间一起下发；读不到时
  界面明说「未读到本机检出」并给出手工核对过的记录值——两种情形在页面上能分辨（`data-version-source`）。
  实测：`.bridge-research/DeepTutor-ef2d9e5c/deeptutor/__version__.py` → `1.6.12`。
- **外链可达性**：`tests/tutor.test.mjs` 对三条外链发一次 HEAD 请求，能连就报状态码，
  连不上（离线/超时）标 `not_run` 并写出原因——网络不可用是环境事实，但「没验证过」会留在输出里。
  最近一次：GitHub 仓库 200，arXiv 论文 200，官方文档超时（`not_run`）。

## 首页六幕叙事的版式约定（2026-10，TODO A3-16 / A3-17 / A3-19）

首页固定舞台（宽 > 1200px 且高 > 700px）里，「动画里的文字」与正文列由**同一条边界**分开：

- **带宽 `--hs-band` 由测量得出**：`(舞台宽 − 正文列宽) / 2`，组件用 `ResizeObserver` 量出后写进根元素。
  遮罩（`mask-image` 的透明区）、大字词的位置与字号、四周带标签的宽度**都从这一个值取**，
  改宽度不会让它们各走各的——旧版把 17% 写死，换到 1280 就出现「清晰可见的标签压在正文列上」（实测「体验」幕 3 条）。
- **带内大字词 / 图记**：五幕是「编号 + 幕名」（`01 主题` 这类大字，在图形**相对**的那一侧带上）；
  **「主题」幕这一格是站点字标做的渐隐水印**（`home-narrative.ts` 的 `bandMark: { src: '/wordmark-256.png' }`，
  2026-10-04 加、同日按用户圈定的区域重排）：位置 `left: 46%`、宽 `min(50%, 60rem)`
  （1440×1000 下 591×182px，中心在舞台的 (73%, 45%)），左端由 `mask-image` 从 `--mark-solid`（0.70）
  渐隐到 0，底色比文字版高一档（0.9，因为大半压在柔光罩之下）。它右端伸到**柔光罩之外**
  （柔光罩只护住舞台的 16%–84%），所以「CS」收笔那一段清楚、左边渐隐——「大一点、透明渐变往中间靠」
  是这么落地的。它是正文**背后**的水印：仍在视觉舞台（z-index 0），柔光罩（1）与正文（2）压在它上面，
  因此「不压正文」这条改由**层序**保证，而不是靠几何回避。
- **舞台左上角的角标**（同一天加，同日两次调整）：「主题」幕的紫色徽记
  （`cornerMark: { src: '/logo-256.png' }`）放在左上角，尺寸 `min(27% 舞台宽, 20rem, 38vh − 5rem)`
  （1440×1000：300px；1220×782：约 200px），柔影是「白色柔光 + 紫色投影」两层。
  第三项上限是按**矮窗口**算的：它让角标下缘停在左侧那摞关键词之上。
  **位置不能从段落顶端起算**：第一幕首屏居中之后，段落顶端其实落在吸顶报头**下面**，
  报头底边离段落顶端 `报头高 / 2 + 3svh`（1440×1000 实测 63px、1280×720 实测 55px）——
  角标若从段落顶端排就会被压住一截。组件因此除 `--home-story-top`（顶栏高）外再量一个
  `--home-story-masthead`（报头高），角标的 `top` 按同一条式子起算、加 2.6rem 余量。
  两处图记都在 `aria-hidden` 的视觉舞台里，`alt` 为空，窄屏形态下整块舞台不渲染。
  验收量的是几何而不是样式串：水印够大（≥ 舞台宽的 35%）、整幅在舞台内、中心落在中右
  （x 45–80%、y 30–60%）、带 `mask-image`、且属于视觉舞台而非正文层；角标落在左上角 30% 区域内、
  整块在舞台内、宽 220–420px、属于视觉舞台，**且在 7 个固定舞台视口里逐档核对「整块在吸顶报头之下」**
  （每档先摆回首屏位置再量——报头那条偏移随视口高变，只在一个视口量过不算数）。
- **四周带标签**每幕 3–5 条（`home-narrative.ts` 的 `sceneLabels`，取自该幕自己说过的话）。
  这是「每幕都有 3–5 条清晰可见的动画文字」这条验收的承担者：位置由带宽算出来，
  任何宽度都放得进，且**只浮现一次**（与正文浮现同一个设计，见文件底部说明）。
- **场景自带的 SVG 文字是纹理**：带宽 < 200px（1280 及以下）时整层让位，只留形状；
  遮罩透明区起点定在 `band − 5%`，因此**可见像素**永远进不了正文列。
  验收按「遮罩后的可见矩形」判定（`tests/home-narrative.mjs`），不是整块文字盒。
- **窄屏（≤1200px 宽或 ≤700px 高）没有动画文字层**：整块视觉舞台不渲染，每幕只有一张静态插图
  （自然流、`aria-hidden`）。于是「文字不入正文列」在窄屏是结构性成立的，
  验收逐条核对「这些层确实不存在 + 静态插图不与正文列相交 + 无横向溢出」。
- **每幕一句可访问描述**：`section[aria-describedby]` 指向 `visually-hidden` 的「画面：<sceneLabel>」，
  标题用 `aria-labelledby`——背景模式下场景自带的 kicker/title 是 `aria-hidden` 的，
  没有这一句，读屏读到的一幕等于空白。
- **对比度与色觉**由机器校验（`tests/a11y-contrast.test.mjs`）：文字令牌 ≥ 4.5:1、边色对画布 ≥ 3:1、
  关系色与契约色在 deuteranopia / protanopia 模拟下要么色差 ΔE ≥ 12、要么另有冗余通道（线型或名字）。
  为此把弱化文字色从 `#7d75a0` 调深到 `#6b6389`（白底 4.26 → 5.57）。
- **面板与画布共用一套强调令牌**（`--emphasis-bg / --emphasis-ring / --emphasis-glow / --emphasis-ink`）：
  浅底 + 描边 + 发光 + 文字变色，画布上的候选卡与面板里的「已加入 / 当前选中」取值同源（TODO A3-22）。

## 工程约定（测试与性能）

- **浏览器验收的运行时**（2026-10 发布前改）：`tests/browser-runtime.mjs` 统一解析
  Playwright 与 Chromium，按「环境变量 `MCS_WEB_PLAYWRIGHT` → `node_modules` 里的
  `playwright` / `playwright-core`」的顺序找，浏览器按「`MCS_WEB_CHROME` → 各平台常见安装位置」找。
  装法：`npm install`（含 `playwright-core`）+ 本机 Chrome / Edge / Chromium，或
  `npm install --no-save playwright && npx playwright install chromium`。
  找不到时脚本**打印怎么装然后跳过**（退出码 0）；CI 设 `MCS_WEB_REQUIRE_BROWSER=1`
  之后跳过变成失败——绿必须是真跑过。从前 19 个验收脚本各自写死某台开发机的缓存路径，
  别人克隆下来必然报 `Cannot find module`。
- **动画页面里的点击**用 `tests/helpers.mjs` 的 `clickInAnimatedPage` / `toggleInAnimatedPage`：
  知识网络的相机动画与节点入场让整页每帧重渲染，Playwright 的「元素稳定」与「点击后状态变化」
  两条检查会和重渲染打架（实测 `Clicking the checkbox did not change its state`）。
  帮助函数改为派发原生 click（SVG 元素没有 `click()` 时退回冒泡的 `MouseEvent`），
  并在给了期望状态时核对**状态真的变了**——避免「点了没反应」被当成通过。
- **动效必须登记**：`web/src/styles.css` 顶部有一份动效清单，本文件里出现的每个 `@keyframes`
  都要在那里写一行并注明 reduce 处理方式（一次性入场 / 循环装饰 / React 降级）。
  `tests/motion-coverage.mjs` 用 CSSOM 取真实 `animation-name` 与之双向比对，
  并在 `reducedMotion: 'reduce'` 下逐页断言「没有任何元素还在动」（含长按拾取等状态场景）。
- **性能回归网**：`tests/network-perf.mjs` 在 227 节点视图上量铺开、重新布局、加节点、开面板的
  端到端耗时与长任务（阈值取实测值的 3–5 倍）。实测：铺开 1516ms、重新布局 483ms（单次阻塞 238ms）、
  加节点 643ms（单次阻塞 393ms）。力导向布局的热循环用 `Float64Array` 并预计算吸力，
  距离用 `sqrt` 而非 `hypot`，`layout()` 从 1474ms 降到 162ms（数字与取舍见 VALIDATION 第五十七轮）。
- **「标签表当选项表」不允许**：筛选选项只能来自真实数据（`buildFacet` 的 `present`），
  标签表最多作为「模板里声明过哪些值」用来如实说明空类别。
  `tests/label-option-scan.test.mjs` 扫描全部 `Object.keys/entries(..._LABELS)` 用法并要求登记理由；
  展示整套词汇的地方（连接类型、契约 mode、站内规模）必须**每行带计数**。
- **设计取值必须可核对**：`TODO.md` 的 B 节列的是「有意选定、不是实验结论」的取值（权重、阈值、几何、时长…）。
  每个取值都在 `data/design-values.mjs` 里登记「住在代码哪一处」+ 一条检查，
  `tests/design-values.test.mjs` 逐条执行（35 条检查：`module` 16 / `css` 9 / `source` 6 / `computed` 4，
  其中源码匹配那层有「不得超过 1/3」的质量约束），并核对 B 节写着同一批取值
  （关键词在、取值列里没有旧值；说明列可以写「原写 X，实测是 Y」）。
  2026-10 首次全表核对抓到 **5 处漂移**（触屏阈值、白雾半径、文字让位、领域词表支数、色相间隔），
  为此把 4 组常量从组件提到可 import 的叶子模块（`ROUTE_DEFAULTS`、`PLACEMENT_SCORE`、
  `CAMERA_*`、`web/src/pointer.ts`）。**改设计取值要同步三处**（代码、登记表、TODO B 节），否则测试会红。

## 未声称的范围

- 没有实现完整 HOL 检查器，也没有检查器自身的机器元证明。
- 没有自动判定 Henkin/标准语义满足关系。
- 没有验证真实教学收益或群体学习规律。
- 规划器是有界参考算法：不承诺工业规模性能或全局最优；Pareto 只产生展示子集。
- 四份机器证书只覆盖局部片段，完整桥梁仍以正文证明与明确义务形式呈现。
- 学习进度只有可追溯的计数与节点名单，没有掌握度百分比、没有间隔重复或到期日排序。
- **没有跑通过真实模型回环**（2026-10）：本机既没有 DeepTutor 后端也没有桥接进程在跑，
  因此 liveVerified 保持 false、页面显示「未验证」，本轮验收里也没有任何一条声称「已连通」。
  要推进这一项，需要本机启动 DeepTutor 与（或）mcs-bridge，跑一次真实会话并把回合 id 与时间记进 VALIDATION。

详细验收记录见 VALIDATION.md；**已知缺口、设计取值与待补证据**集中在 [TODO.md](TODO.md) ——
那份清单由各轮验收记录的「未落实 / 边界」小节汇总而来（117 条原始条目 → 38 项缺口 + 12 项设计取值 + 8 项待证据事项）。
