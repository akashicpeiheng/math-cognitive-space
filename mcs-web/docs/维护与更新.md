## 2. 先判断更新类型

| 更新类型 | 修改入口 | 必做检查与边界 |
| --- | --- | --- |
| 教学正文、节点、关系、证据 | data/ 的权威源；生成文件回到生成器与输入修改 | 本体自检、全量回归；人工核对动机、条件反例、数学与引用；记录本体哈希 |
| 页面与学习交互 | web/ | build、check、全量回归；预览核对手机/桌面、公式与关键学习操作 |
| API、规划器、认证、存储 | server/、core/、shared/ | check、全量回归与相关公网场景；涉及迁移时先隔离演练 |
| 理论文稿 | mcs-foundations/ 分章 Markdown | 有限模型与相关证书验证；不把有限检查升级成一般证明 |
| 域名、回调、环境配置 | 阿里云、托管平台、认证服务 | 单独列出旧值/新值、影响与回退；配置秘密不写发布记录 |
| 纯维护文档 | docs/、状态与待办文档 | 链接、路径、状态一致性与导出检查；不冒充重新完成了全量功能验收 |

M 是版本化公共内容，E 是学习者状态，D 由 M + E 派生。学习行为不回写 M。
流水线生成件经过人工内容核验和明确节点映射后才进入公共内容；归档完成不等于数学审核完成。

## 3. 本地检查与候选包验收（已有入口）

先查看当前改动与并行工作。若有人正在修改同一工作区，选择稳定快照或独立检出验收；
不要一边继续改源文件，一边把检查结果记到另一份版本上。

在 `E:\MCS\mcs-web`：

```powershell
npm run build -- --outDir E:/MCS/mcs-web/tmp/candidate-dist
$env:MCS_WEB_TEST_STATIC_DIR = 'E:/MCS/mcs-web/tmp/candidate-dist'
npm run check
$env:MCS_WEB_REQUIRE_BROWSER = '1'
$env:MCS_WEB_REQUIRE_TLS = '1'
npm test
```

开发目录同时被公网服务使用时，上述独立构建避免测试前就替换线上文件。`MCS_WEB_TEST_STATIC_DIR` 只控制测试服务，
不改变正式配置；未设置时使用默认 `web/dist`。任何一步非零退出都应处理后再发布，结束后恢复三个测试环境变量原值。
需要 Node、Python、浏览器与 TLS 检查所需环境；必需场景缺条件就是未完成。
允许缺材料的跨仓库检查要逐项记录原因，不要求伪造一个“零跳过”。

日常定位可先运行 `npm run test:core`、`npm run test:api` 或定向用例；
源码发布仍以稳定候选包的完整约定检查为准。旧站、联动服务若修改，分别执行其 AGENTS.md 规定的检查。

前端修改需重新构建。已经运行的 Node 服务不会因重新打开浏览器而重载服务器代码；
一键入口只保证服务存在。重启应明确区分本机实例和公网实例，避免中断另一项工作。

## 4. 导出与 GitHub 更新（公开包已有，PR/CI 规则待建立）

1. 选定稳定的开发版本，记录本地提交和未提交补丁状态；公开候选包的文件哈希用于固定本次实际内容。
   `.tmp-shadow` 已于 2026-10-08 确认为指向权威 `web/src`、`web/public` 的临时预览树，并按精确路径排除。
   原目录原样保留，其他符号链接/目录联接仍会阻断；不要扩大为“忽略所有点目录”或关闭联接检查。
2. 从开发源导出到一个不存在或为空的新目录。在仓库根运行以下命令，先替换目录中的发布编号：

```powershell
node mcs-web/scripts/export-open-source.mjs --out E:\MCS\_ops\releases\YYYYMMDD-NN
```

3. 阅读目录外的导出报告：阻断项为零，必需文件齐全。开发源应完成本地禁用词表检查；
   公开克隆缺该表会报告 `disclosuresChecked: false`，不能写成检查通过。人工复核绝对路径提示与内容范围。
4. 在候选包的 `mcs-web` 中安装锁定依赖（`npm ci`），运行 build、check 和严格 `npm test`。
   记录代码与报告对应关系，不只保留最后一行成功文字。
5. 发布副本先 `git fetch origin`，核对远程 `main` 和本地差异。存在别人的改动时先整合，不强推或重写历史。
6. 从当前远程主线建立 `codex/<主题>` 分支。按候选包清单同步文件，保留 `.git`；
   先看拟新增、修改、删除清单，逐项确认删除仍在发布范围内。不要对开发根或历史目录运行整目录镜像删除。
7. 查看完整差异，特别核对 `.github`、平台配置和许可证，提交并推送该分支，建立 PR。
   GitHub 上合并的修复要同步回开发源，否则下次导出会把它覆盖。
8. CI 和预览通过后再合并。发布前已有授权时按授权继续；仅提出规划不会自动执行公开推送或正式切换。

**2026-10-09 的实际做法与差距**：仓库此时还没有 CI 与必需检查，第 6–7 步的分支 + PR 无法形成有效门槛，
因此本次同步按「第 1–4 步照做、第 5 步核对远程后**直推 `main`**」执行，并在 `VALIDATION.md` 第九十轮
如实记下这条差距。建立 CI 与分支保护（R3c）之后，应回到分支 + PR 的流程，而不是把直推当成常规。

**待补的自动化**：

- 根级 `.github/workflows` 的权威来源与导出规则。目前导出器没有复制根级 `.github/`、`vercel.json` 的专门条目，接入时需一并调整、验证。
- 公开包 CI：锁定依赖安装、build、check、严格浏览器/TLS 回归、导出检查；不得依赖作者电脑的私有材料。
- `main` 要求 PR 和实际存在的必需检查，禁止日常强推；单人项目不要求不可满足的自审批准。
- 先跑出真实检查结果再设为必需状态。[GitHub 分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 5. 预览、正式发布与版本记录

当前服务直接运行开发源。第一步应建立独立运行副本、固定启动版本，并让数据库、扩展与秘密使用受保护的持久位置；

未来接入 Vercel 时可使用 Git 分支预览，仍要隔离认证与后端数据。[Vercel Git 部署](https://vercel.com/docs/git)

**预览最低验收**：

- 首页、开始学习、节点详情、公式与深层页面刷新正常；手机直连与桌面各检查一次。
- 涉及首页/网络交互时，固定前端资源版本后在小米平板 Edge 横竖屏复测滚动闪白、顶栏、双指缩放与单指接续；核对末幕入口、桌面操作和减少动态效果。模拟触摸与降频性能测试单列，不代替真机结果。
- 访客可读公共内容；个人档案接口未登录为 401；两个账号的笔记、记录、视图互不可见。
- GitHub 登录、退出、CSRF 校验与同源代理正常；回调的动态 state 可匹配且经服务端校验。
- 保存记录/笔记/网络视图后可重读；规划提交与轮询能在任务限额内完成。
- 后端重启后持久数据、账号归属、草稿、扩展包仍在；未完成的进程内任务如实报告，不能静默装作完成。
- 缺模型、发信或证书环境时界面准确说明；证书校验失败不能显示“已认证”。

**当前自托管路线的正式切换目标**：

1. 固定待发布提交，记录前端与后端版本、本体哈希、数据结构版本、配置修订号和上一稳定版本。
2. 完成一致备份；数据库变更先采用新旧代码可兼容的增量迁移，破坏性步骤另设窗口。
3. 先在隔离环境验收，再按依赖顺序部署兼容后端与前端；有写入影响时明确窗口与恢复条件。
4. 在运行副本隔离完成后，切换源站到已验收候选；保留上一份代码与匹配配置，独立保存用户数据。
   当前脚本仍硬指向开发目录，修改启动目标属于待实施改造；不能仅导出文件就写“线上已更新”。
5. 保留现有固定域名与命名隧道，核对实际服务的版本和本体哈希。规划任务仍在进程内，重启前处理在途任务并记录中断边界。
6. 在正式域名检查 HTTPS、健康接口、深链、登录及一次受控保存/重读；留下脱敏结果后标记发布完成。

## 6. 数据备份与恢复

**代码回退与数据恢复是两件事。** GitHub 不能替代用户数据库备份，前端部署回退也不会恢复后端数据库。

| 对象 | 当前自托管形态 | 目标托管形态 | 必须核对 |
| --- | --- | --- | --- |
| 学习数据 | 独立公网 SQLite | PostgreSQL | 记录计数、事件、笔记、视图、修订号 |
| 会话与对象归属 | 独立 auth.sqlite3 | 相应 PostgreSQL 业务表 + Supabase Auth 身份 | 用户 ID 与归属关联；身份提供方自身的恢复能力另外核对 |
| 编写库 | authoring.sqlite3 | 持久卷或后续适配的数据库 | 草稿、审阅、发布关系 |
| 公共扩展 | extensionsDir 指向的文件 | 持久卷或版本化对象存储 | 包、清单、本体哈希与编写库一致 |
| 私有配置 | _ops/runtime 下的实际配置 | 托管平台受保护配置 | 配置版本与受保护备份，不公开凭据 |
| 命名隧道恢复材料 | 运行脚本所用 cfhome 与隧道配置 | 目标连接器的受保护凭据 | 能重新建立固定入口；凭据不进入公开候选包 |

先查目标实例的实际配置，不因文件名相似就备份了本机库而漏掉公网库。
`backup.mjs`、`restore.mjs` 面向学习存储，不等同于整站备份/恢复。

- 当前 SQLite 备份实现是 checkpoint 后复制文件，未验证多库并发一致性。
  手工备份应在安排好的停写窗口确认全部目标写入进程停止后，保存所需库、伴随文件、扩展与配置到新目录；不手工删除 WAL。
- 不停机备份须先实现并验证一致性快照，再协调多库与文件的共同备份点。[SQLite 官方备份说明](https://www.sqlite.org/backup.html)
- PostgreSQL 需要数据库层一致快照/备份；不能把跨多个查询、未经快照验证的 JSON 导出自动称为一致整库备份。
  学习者导出也不包含所有账号、认证服务和发布文件。
- 每份备份记录源实例、应用版本、时间、文件 SHA-256 和必要计数。受保护异机副本与恢复演练不可缺省。
- 先在新目录或独立数据库恢复，检查一条学习记录、账号归属、草稿及本体版本。
  确认恢复对象和数据损失范围后才切换；不覆盖原库来做第一次演练。

建议保留期与恢复目标见规划第 6 节，目前尚未配置定时备份、删除策略或停机任务。

## 7. 故障与回退

| 症状 | 首先检查 | 恢复动作 |
| --- | --- | --- |
| 新域名无法解析 | 阿里云注册/NS 委派，Cloudflare 当前权威记录与公共 DNS | 在当前权威 DNS 处修复；不把阿里云云解析当作当前网站的记录来源 |
| Vercel 首页正常而 API 失败 | 后端健康、重写顺序、Host 白名单、版本兼容 | 恢复匹配的前后端组合，不只重发静态页面 |
| 登录回到 localhost 或临时地址 | publicOrigin、Site URL、重定向匹配与 Cookie | 对齐正式域名配置后重试真实登录 |
| 能读不能保存 | Origin、CSRF、登录身份与归属 | 修正确认过的代理/配置；不通过关闭鉴权“恢复” |
| 规划一直轮询 | 后端任务状态、重启记录、实例数量 | 识别被中断任务并提示重新提交；排查前不扩成多实例 |
| 更新后数据不见 | 实际连接的库、持久卷、归属和数据结构版本 | 停止有害写入并保护现场，在隔离副本判断是否要恢复 |
| 隧道入口失败 | 隧道与源站是否都在运行 | 查看对应日志；状态码本身不能唯一确定故障原因 |

回退顺序：停止继续发布 → 保留故障证据 → 选择兼容的上一应用版本 → 验收 → 记录原因并修复主线。
Vercel Instant Rollback 只切回已有部署；不会自动回退外部后端、数据库或重建环境变量。[回退说明](https://vercel.com/docs/instant-rollback)

如果新版本已改变数据结构，先检查旧版是否兼容；无法兼容时优先前向修复。
恢复旧备份会丢掉备份之后的写入，需单独评估，不能把用户数据跟着代码一起倒退。
DNS 切换也不能取代应用回退。
