# 维护与更新流程

这份文档回答一个问题：**改完之后，怎么让改动安全地到达"本机"、"公网"、"GitHub"三个地方。**

三个地方是**分开的**，别混：

| 地方 | 谁在看 | 怎么生效 | 数据在哪 |
|---|---|---|---|
| 本机工作台 | 你（`http://127.0.0.1:3784`） | 双击 `E:\MCS\打开MCS网站.cmd` | `mcs-web/runtime/*.sqlite3` |
| 公网站点 | 访客（`https://<随机名>.trycloudflare.com`） | 跑 `E:\MCS-run\start-public.cmd` | `mcs-web/runtime/public/*.sqlite3` |
| GitHub 仓库 | 开源读者 | 导出 → 镜像 → `git push` | 无（数据不进仓库） |

---

## 1. 日常改动的闭环

    cd E:\MCS\mcs-web
    npm run check        # 本体与机器证书自检（doctor）：本体哈希、形成检查、角色模板、
                         # 局部化登记，以及四份机器证书的重放与摘要核对
    npm run build        # ★ 改了 web/ 下的任何前端文件就必须跑（tsc --noEmit + vite build → web/dist）
    npm test             # 全量验收：核心数学、API、浏览器端到端

想快一点时可以只跑一部分：

    npm run test:core         # 核心（本体 / 规划器 / 本地化 / 导师）
    npm run test:api          # HTTP 接口层
    npm run test:browser      # 浏览器验收（需要 Playwright）
    npm run verify:relations  # 重放四案例机器证书，核对摘要

> 浏览器验收在**缺浏览器时是"跳过"而不是"失败"**。要做发布前的严格判断，
> 用 `MCS_WEB_REQUIRE_BROWSER=1` 把跳过变成失败——否则"绿"可能是假的。

改完在本机看一眼：关掉旧窗口、重新双击 `E:\MCS\打开MCS网站.cmd`。

---

## 2. 让改动对公网生效

公网站点跑的是**这份工作副本**（`node server/index.mjs`，端口 3785），所以改动生效只要重启：

1. 在跑公网的那个窗口按 **Ctrl+C**；
2. 重新跑 `E:\MCS-run\start-public.cmd`；
3. 窗口会打印**新的公网地址**（每次都不一样）。

**前端改动必须先 `npm run build`**：服务端只发 `web/dist` 里构建好的静态文件，不跑 Vite 开发服务器。

改完地址后，两种情况：

- Supabase 的 Redirect URLs 里已有 `https://*.trycloudflare.com/**` → **什么都不用改**；
- 没有 → 每次都要把新地址加进去，否则登录会把你丢到 `http://localhost:3000`。

查当前地址的两种办法：看窗口，或看 `E:\MCS-run\cloudflared.err.log` 里最后一条 `https://…trycloudflare.com`。

## 3. 发布到 GitHub

**发布闸门是导出脚本的审计**：它会检查必需文件是否齐全、有没有禁用路径（私人材料、
历史快照）、有没有密钥形状的字符串、有没有作者机器的绝对路径。**审计不过就不要推。**

    cd E:\MCS\mcs-web
    node scripts/export-open-source.mjs --out E:\MCS-release-<日期>

    # 看最后一行的结论，必须是「导出规则检查通过」
    # 然后再镜像进发布暂存区（.git 不能被覆盖）
    robocopy E:\MCS-release-<日期> E:\MCS-publish /MIR /XD .git /NFL /NDL /NJH /NJS /NP

    cd E:\MCS-publish
    git add -A
    git status --short            # ★ 确认改动范围符合预期再提交
    git commit -m "…"
    git push origin main

两条纪律：

1. **开发目录（`E:\MCS`）不直接推**——它有 `reference/`、`design/`、`MCS_vault/` 等
   不进开源包的材料；发布只从 `E:\MCS-publish` 走。
2. **推送前先 `git fetch origin && git status -sb`**。这个仓库曾被并行会话重写过历史
   （压缩成一个提交），也出现过两边同时写的情形；先看一眼再推，比事后收拾便宜。

## 4. 数据与备份

**2026-10-05 更新：公网备份与隔离恢复尚未演练，是下一阶段优先项。**
维护脚本的自动测试只覆盖临时学习库，不能替代多库和扩展包的实际恢复。

| 文件 | 内容 | 丢了会怎样 |
|---|---|---|
| `runtime/public/mcs-web.sqlite3` | 公网访客的学习数据 | **真丢**，不可重建 |
| `runtime/public/auth.sqlite3` | 登录会话、OAuth 中间态、对象归属 | 不仅退出登录，还可能丢失学习记录与账号的归属关联 |
| `runtime/public/authoring.sqlite3` | 公网实例的编写库草稿 | 草稿丢失（容器/重启场景本来就临时） |
| `runtime/mcs-web.sqlite3` | 你本机工作台的数据 | 本机数据丢失 |
| `E:\MCS-run\public-config.json` | 公网配置（含会话密钥） | 需要重填 Supabase key；会话密钥变了 = 所有人重新登录 |
| 配置指向的 `extensionsDir` | 已发布的公共扩展包与版本记录 | 编写库和本体扩展可能失配，不能靠恢复学习库补回 |

**先确定备份方案，再安排执行**：备份目录、保留期和停机窗口需要确认，不能把用户数据库复制到公开发布目录。

1. 先核对目标实例的实际配置：本机库与公网库不是同一份；不要默认运行 `backup.mjs` 就备份了公网实例。
2. 当前 SQLite 驱动是 checkpoint 后复制文件，并非 Online Backup API；本轮未验证并发写入下的一致性。
   当前手工备份应在用户同意的停机窗口中，确认目标实例的所有写入进程关闭后，
   将三库、仍存在的 WAL 等伴随文件、扩展包与配置一起保存到新的受保护目录；不手工删除 WAL。
3. 若需不停机备份，先实现并验证 SQLite 的一致性快照方式（Online Backup API / `VACUUM INTO`），
   再处理多库与文件之间的共同备份点。边写入边逐个复制 `.sqlite3`、`-wal`、`-shm` 不保证一致。
   依据：[SQLite 官方备份说明](https://www.sqlite.org/backup.html)。
4. 记录版本、文件 SHA-256 与必要计数；在隔离目录恢复，核对完整性、归属和一条学习记录的可读取性。
   配置包含密钥，备份必须限制访问，不能上传 GitHub 或贴到聊天。

**恢复学习库**：`node scripts/restore.mjs <备份文件>` 会替换所配置数据库中的学习数据，先停服务、
先保护现状、先在隔离副本演练；它不会自动恢复账号库、编写库或扩展包，不等于整站灾难恢复。

## 5. 配置与凭据

- **能进仓库的**：`render.yaml`、`Dockerfile`、`.dockerignore`、文档、示例配置（`config.example.json`）。
- **不能进仓库的**：`config.local.json`、`E:\MCS-run\public-config.json`、任何连接串与密钥。
  导出脚本的密钥模式检查是兜底，不是许可。
- **Publishable key** 是公开值（浏览器里就有），可以放配置、可以贴给人；
  **数据库密码、`service_role` key、会话密钥**永远不要外发。
- 改 `MCS_WEB_AUTH_SESSION_KEY` = 让所有人重新登录。除非怀疑泄露，别动它。

## 6. 故障对照表

| 症状 | 多半是什么 | 怎么处理 |
|---|---|---|
| 页面 **530** | 源站没起来（窗口关了，或启动被自检拒绝） | 看窗口里有没有 `MCS Web 已启动`；没有就照它那句错误改配置 |
| 启动失败 `getaddrinfo ENOTFOUND xxx` | 窗口里有 `MCS_WEB_DB_URL` / `DATABASE_URL` 残留，盖掉了配置 | `Remove-Item Env:\MCS_WEB_DB_URL`；启动脚本现在会自动清并提示 |
| 登录后落在 `http://localhost:3000` | Supabase 的 Site URL / Redirect URLs 没配 | 见 `部署清单.md` 第 7.5 节 |
| 登录报「登录回调无效」 | state 过期（10 分钟）或换了域名重开 | 重新点一次登录 |
| 脚本报语法错、中文变乱码 | 文件存成了**无 BOM** 的 UTF-8，而 PowerShell 5.1 按 GBK 读 | 另存为 **UTF-8 with BOM** |
| 改了前端却看不到变化 | 没 `npm run build`，或没重启脚本 | 先 build 再重启 |
| 端口被占 | 3784 = 本机，3785 = 公网，重复启动了 | 先关掉旧窗口 |
| `npm test` 一片绿但你没配浏览器 | 浏览器验收被"跳过"当成了通过 | 用 `MCS_WEB_REQUIRE_BROWSER=1` 重跑 |

## 7. 什么时候该搬家

现在是「本机 + 快速隧道」，两个硬约束：**电脑要开着**、**地址每次会变**。出现下面任一情况就该搬：

| 诉求 | 搬到哪 | 需要什么 |
|---|---|---|
| 地址固定，仍在自己机器 | **域名 + Cloudflare 命名隧道** | 域名 ¥10–30/年（支付宝可付），一次性配置 |
| 不想让电脑常开、免费 | **Render** | 境外信用卡（`render.yaml` 已就绪） |
| 想完全自己掌控 | **香港 / 新加坡轻量服务器** | 支付宝可付；`Dockerfile` 已就绪，`docker run` 即起 |

搬到"机房"那两条时**必须换掉本地 SQLite**：容器磁盘会在重启 / 重新部署时清空，
学习记录不是缓存。步骤是：

1. Supabase 或自建 PostgreSQL 拿到连接串（**主机名要含 `pooler`**）；
2. 设 `DATABASE_URL` + `MCS_WEB_DB_SSL=require`（Supabase 用私有 CA，硬校验链会失败）；
3. 把 `runtime/public/*.sqlite3` 里的数据按逻辑导入（`db.dumpAll()` / 导入接口，
   全有或全无，失败会整体回滚）；
4. **不要**在容器平台上设 `MCS_WEB_ALLOW_LOCAL_DB=1`——那个开关是给"自己的磁盘"用的，
   在容器上等于主动选择丢数据。

## 8. 一句话版本

- **改** → `npm run check` + `npm test`（必要时 `MCS_WEB_REQUIRE_BROWSER=1`），前端记得 `npm run build`；
- **上公网** → 重启 `E:\MCS-run\start-public.cmd`，地址变了就再发一次（白名单配了通配符则免）；
- **上 GitHub** → 导出脚本审计通过 → 镜像进 `E:\MCS-publish` → 提交推送；
- **保数据** → 确认目标实例与一致性备份方案，覆盖三库、扩展包、配置，并实际做隔离恢复演练。
