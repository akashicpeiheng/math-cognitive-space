## 2026-10-13 续验：性能与 Lean 运行方式

网络加节点的 CPU 剖析发现，候选评分重复计算与新节点无关的旧边交叉，每次自动位置落盘与面板测量还会重新运行力导向布局。现仅计算受候选位置影响的交叉对，把旧边之间的常量从候选比较中移除；统计结果仍计算全图交叉数。布局基线独立缓存，手动位置优先及自由/学习顺序/逻辑核心模式保持原规则。新增独立对照用例在 81 个候选位置及退化边上核对“局部交叉数 + 固定旧边交叉数 = 全量交叉数”。

实际 Chrome 性能复测：335 节点视图，新增节点 584 ms，最大单次阻塞 515 ms，通过原 3000 ms / 800 ms 门限；全图重排 433 ms，最大阻塞 194 ms。25 项摆位/顺序单元测试及两个相关真实浏览器回归通过。没有提高性能门限。

Lean 运行方式修复经过诊断与正式验证：Lake 仅捕获编译环境后退出，原生 Lean 依次重编译六个项目模块；单进程顺序调用官方 `LeanChecker.replayFromImports`，然后逐目标核对八个定理与传递公理。全部原生命令使用 `-j 1`；测试文件顺序执行，减少同机并发。五个模块的完整成功标记、工具链与导入检查模块摘要是通过的必要条件。仍限制 120 秒 / 4 MiB，没有放宽目标、公理白名单或增加自动重试。

中间完整回归再度遇到审计读取标准库文件失败（19 项中 18 项通过，七类真实负例全部拒绝），日志保留于 `tmp/writing-followup-full-test.log`。限制工作线程后，两份 HTTP 正例通过；正式维护报告分别为 64000 ms 与 64460 ms，`ready` 和要求真实 Lean 的 doctor 通过。数学源、固定依赖与工具缓存未改；检查入口和策略变更后明确重新封存并生成新报告，旧收据继续作为历史保留，原文对应审阅仍为 pending。详细摘要与过程见[Lean 续验记录](../LEAN-验收记录.md)。

最终回归从 Lean 组继续，要求 `MCS_WEB_REQUIRE_LEAN/BROWSER/TLS=1`，使用默认 120 秒任务预算；前四组使用刚才完整回归中的通过记录。`tmp/writing-followup-resumed-test.log` 的前 28 组均通过，包括 Lean 19/19、中英重放与下载、账号权限中的真实重放。第 29 组 HTTPS 的真实 Lean 重放亦通过，但“沿路线阅读”在 URL 跳转后立即读取了尚未加载的正文，导致整组失败。

该用例补充等待 `.node-header h1` 可见，再执行原有正文长度断言；不能把加载占位文字作为已完成阅读，也没有修改网站行为或降低断言。随后从 HTTPS 组继续运行，日志为 `tmp/writing-followup-https-and-rest-test.log`，48 组全部通过、退出码 0；此前各次失败日志完整保留。

最终合并为 **80/80 组通过**：第 1–4 组取最新完整启动回归中的通过前段，第 5–32 组取 Lean 续验的通过前段，第 33–80 组取 HTTPS 及后续完整通过段。不是一次不中断的全绿运行。当前列表含“从零走范例路径”的新增独立步骤，故与首次候选的 79 组历史统计不同。[工程验收汇总](工程验收汇总.json)逐项列出当前 80 组、三段日志范围及 SHA-256。各段均要求真实 Lean、Chrome 和 HTTPS，未提高资源或性能门限。
